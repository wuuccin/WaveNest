## 1 待修缺陷

缺陷名称：回放补齐帧在重启后丢失。

| 项目 | 内容 |
|---|---|
| 现象 | 飞行途中重启后端后，查询回放接口返回的轨迹缺失重启前那一段，重启前帧为空；实时推送自动重连与订单续跑到完成均正常 |
| 根因 | `wl-m4-monitor` 的 `FlightRecordStore` 用进程内内存 `ConcurrentHashMap` 存轨迹，进程重启即清空。这属于存储选型的技术债，不是算法错误、不是环境异常、也不是测试写错 |
| 修法 | 存储介质由内存改为 Redis。四件套已起 Redis，后端重启不影响 Redis 里的数据。`append`、`replay`、`flightIds`、`statistics` 四个方法签名不变，下游零改动 |
| 主负责人 | 彭紫情，负责 M4 存储与清洗，主改 |
| 配合 | 宋冰鑫负责验证告警位置回放在 Redis 下仍正确；吴可欣负责收口裁定选型 |
| 改动位置 | 第一，`FlightRecordStore.java`，唯一核心改动，键为 `flight:track:{flightId}`，用 zset 按时间戳排序，值为遥测状态 JSON；第二，`wl-m4-monitor/build.gradle` 加 Redis 依赖；第三，`application.yml` 配 Redis 连接，复用四件套已有的 redis；第四，三个测试文件中六处直接构造存储实例的代码改为连测试 Redis，或保留内存子类并用测试 Bean 覆盖 |
| 验收判据 | 第一，重启后回放返回重启前与重启后的完整帧，重启前段非空；第二，原六处单测通过，含回放控制器的三条用例；第三，实时推送、订单续跑、告警落库与位置回放不退化 |
| 期限 | 当日完成并合入 `develop` |

## 2 完成顺序

彭紫情先完成核心改动并自测通过，宋冰鑫再做告警位置回放验证，最后由吴可欣收口裁定。

宋冰鑫的验证依赖彭紫情的改动，必须在 Redis 版存储上验，二者不可并行。
