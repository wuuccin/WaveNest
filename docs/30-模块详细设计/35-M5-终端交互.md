## 1 模块定位与边界

M5 是整个系统的**展示与交互层**：向上接收并呈现 M1 数据采集、M2 调度引擎（含常驻层的船舶状态估计与预测）、M3 动态会面与路径规划、M4 飞行任务监控的运行结果，向下通过后端读写 M6 数据库与缓存的持久化数据。

它只做两件事——**把算法层算出来的东西画给人看，把人的干预指令转成请求发给 M2**。兜底保障与实时追踪是贯穿全程的横切机制，不作为独立模块单列。

| 本模块负责 | 本模块不负责 |
|---|---|
| 地图渲染、轨迹与会面点绘制、告警展示 | 任何业务决策（接单判断、可行性判断、是否返航） |
| 船员下单、调度员人工干预的界面与交互 | 直接调用算法模块 |
| 把后端下发的态势数据实时刷新到页面 | 提供「把货物直接改派给另一架机」的能力 |

一条硬边界：**不提供「把货物改派给另一架机」**——同一件货物同一时刻只能在一个载体上，换机须先回收。起飞前换机是真的可行（货还在巢里），因此界面上允许的是「撤回尚未起飞的订单」。

## 2 形态选型

**做 Web 网站，不做桌面软件。** 三个入口统一用一套 Web 前端工程产出。

| 对比维度 | 桌面软件（Electron、Qt 等） | Web 网站 |
|---|---|---|
| 现场演示 | 需提前在评委电脑上安装，版本不匹配或缺依赖就翻车；换设备又要重装 | 评委打开浏览器输入网址即可看，投屏、平板、手机都能访问 |
| 分发与跨端 | Windows、macOS 要分别打包，船员端还得另做手机端 | 一套代码适配 PC、平板、手机、大屏；船员 H5 直接在手机浏览器打开 |
| 迭代更新 | 改一个 bug 要重新打包、重新分发，现场临时改不了 | 改完部署即生效，答辩前一晚发现问题当晚能更新 |
| 开发成本 | 需同时掌握桌面框架与打包工具，团队人少不划算 | 前端三件套（框架、地图、图表）生态成熟，上手快 |
| 实时性 | 需自己封装网络通信 | WebSocket 原生支持 |

工程组织：三个入口不做三个独立项目，而是**同一套前端工程下的三个路由**，共用地图组件、请求封装与样式体系。

## 3 功能分解

### 3.1 船员端 H5

面向船上人员，目标是「单手能操作、弱网能用」。

| 页面或功能点 | 内容 | 数据来源 |
|---|---|---|
| 下单页 | 选择本船（或按 AIS 列表点选当前位置）；选物资类型、填重量、选紧急程度（普通、紧急、特急）；填联系人与备注，一键提交 | 提交后经后端进入 M2 的接单判断 |
| 订单状态时间线 | 可视化流转：待调度 → 已派发 → 去程中 → 末段交接中 → 返航中 → 已完成；异常分支只显示异常终止，迫停与迫降的落点单列展示。每步显示时间 | M6 订单状态 ＋ WebSocket 推送 |
| 飞行中实时卡片 | 预计到达倒计时、无人机当前位置缩略图、会面点是否已锁定 | M3 会面点 ＋ M4 遥测 |
| 历史订单 | 本船历史订单列表与结果（成功、货物回收后重派、放弃） | M6 查询接口 |

### 3.2 调度后台

| 页面或功能点 | 内容 | 数据来源 |
|---|---|---|
| 订单列表 | 多订单并发下的看板：按状态或优先级筛选，显示每单当前走到流程第几步 | M1、M2、M4 |
| 无人机与机巢状态面板 | 每架机：位置、电量、当前任务、预计归巢时间；每个机巢：巢位占用、可用实例数 | M4 遥测 ＋ M6 |
| 人工干预操作台 | 调整会面点（调整后由 M2 重算航迹并重新校验可行性）；撤回尚未起飞的订单；取消订单；紧急叫停某单；一键冻结派单（对应 M2 的运行开关·气象熔断）；转人工接管。不提供「把货物直接改派给另一架机」 | 指令回传 M2 |
| 事件日志流 | 兜底事件实时滚动：电量告急、风速突变、通信中断、失联、意图变更（6b）、空域冲突等 | 横切兜底机制 ＋ M3 的 6b 意图变更判定 |

「调整会面点」这条操作有下游链路：改完之后由 M2 重算航迹并重新校验可行性；否则它是一条断掉的操作。

### 3.3 REST 接口

| 接口 | 方法 | 用途 |
|---|---|---|
| `/api/orders` | POST、GET | 船员下单；调度后台拉订单列表 |
| `/api/drones`、`/api/nests` | GET | 机队与机巢状态 |
| `/api/intervene` | POST | 调度员调整会面点、撤回订单、取消、冻结派单 |
| `/api/replay/{taskId}` | GET | 时间轴回放取历史帧数据 |

字段与消息格式的权威定义见 `22-接口契约` §3、§4。

### 3.4 页面路由

| 路由 | 对应入口 |
|---|---|
| `/h5/order`、`/h5/track/:id` | 船员端 H5（下单、订单追踪） |
| `/admin/` | 调度后台 |
| `/screen/` | 可视化大屏（见 `36-M5-可视化`） |

## 4 关键设计

### 4.1 前端不碰算法

所有数据经后端中转，前端只负责渲染与收集指令。前端与算法同学最容易扯皮的地方是数据格式，必须在开工前定死（见 `22-接口契约` §7）。

### 4.2 兜底与追踪是横切机制

两者没有独立的数据流入口和出口，全程挂在其他环节上，因此不单列模块；界面上表现为事件日志流与告警图层。

### 4.3 订单状态时间线是投影

时间线展示的是 `order_task.status`，而订单状态在任务期间是任务状态的投影（见 `23-状态机定义` §5）。界面不再单独维护一条时间线。

### 4.4 干预动作的边界

| 允许 | 不允许 |
|---|---|
| 调整会面点（M2 重算并复校） | 把货物改派给另一架机 |
| 撤回尚未起飞的订单 | 直接指定另一架机接管在途货物 |
| 取消订单、紧急叫停、转人工 | 越过 M2 直接指挥 M3 或 M4 |
| 冻结派单（气象熔断的人工入口） | — |

## 5 数据读写需求

| 数据 | 读 | 写 |
|---|---|---|
| 订单、任务状态 | `order_task`、`mission` | 订单创建；货物「已就绪」的人工确认 |
| 无人机与机巢 | `drone`、`nest` | — |
| 告警 | `alert` | 处置记录（处理人、动作、时间） |
| 货物 | `goods` | 未就绪 → 已就绪；野外迫降回收后的人工确认 |
| 干预与熔断记录 | `task_log` | 触发人、时间、原因、影响范围 |

本模块**不直接建表**，读写均经后端统一访问接口；表结构以 `37-M6-数据库` 为准。

## 6 技术选型

| 环节 | 选型 | 理由 |
|---|---|---|
| 前端框架 | Vue 3 ＋ Vite（或 React，团队熟哪个用哪个） | 生态成熟、上手快，单页应用适合三个路由入口 |
| 2D 地图 | Leaflet ＋ 天地图或 OpenStreetMap 沿江底图 | 2D 足够且加载快；Leaflet 轻量，自定义 marker、虚线、图层切换方便。**不上 3D**——现场 2D 更稳 |
| 实时通信 | WebSocket（主），SSE 或轮询（降级） | 态势、遥测、告警都要秒级推送；断连自动重连 |
| 图表 | ECharts | 能耗对比柱状图、预测误差曲线、统计卡片 |
| 状态管理 | Pinia（Vue）、Zustand（React） | 管理全机队实时状态，避免每个组件各拉一遍 |
| 请求封装 | 统一封装 REST 调用与错误处理 | 三个入口共用 |
