## 1 模块定位与边界

本模块是 M6 的**高频读侧**：把实时最新状态放进 Redis，保证调度与监控的高频查询低延迟，历史与低频数据落 MySQL。

| 做 | 不做 |
|---|---|
| 实时状态的缓存读写 | 不判断数据是否该更新——由业务模块决定并写入 |
| 提供统一访问接口，业务模块不直接碰存储 | 不承载业务决策 |
| 与库的最终一致（异步落库、失败补偿或告警） | 不承担历史归档 |

---

## 2 缓存范畴

进 Redis 的是**实时最新**四类：

| 范畴 | 内容 | 主要消费方 |
|---|---|---|
| 船舶态势 | 船舶最新状态与常驻预测快照 | M2、M5 |
| 无人机实时状态 | 状态、电量、位置 | M2、M4、M5 |
| 气象实时 | 最新观测与「某位置某时刻风」查询 | M2、M3 |
| 活跃占位窗口 | 尚未释放的占位时隙 | M2 |

落 MySQL 的是**历史与低频**：`ship_ais` 历史、`flight_point`、`task_log`、各档案表（`nest`、`drone`、`goods`、`order_task`、`weather` 历史、`hydro`、`airspace_restriction`、`emergency_landing_point`、`alert`、`sys_param`）。

判断标准：**需要秒级反复读且只关心「最新」的进缓存；需要回溯、统计、审计的落库。**

---

## 3 读写策略

1. 更新状态时**优先写 Redis，成功后异步落 MySQL**。
2. 落库失败必须**补偿或告警**，不允许静默丢失（细则见 `27-一致性约束` §4）。
3. 提供统一数据访问接口（DAO 或 Repository），业务模块不直接操作 Redis 或 MySQL。
4. 坐标与单位归一在本层同样生效：入缓存与落库都归一到基准坐标系与标准单位（见 `37-M6-数据库` §4）。

---

## 4 与库的一致性

本模块自身不做一致性判定，遵循 `27-一致性约束` 的三条要求：

1. 占位是**原子操作**，与时间窗校验同一事务（涉及 Redis 的活跃占位窗口与库中时隙台账）；
2. 状态流转由业务模块写入，订单与任务在任务期间同事务同值；
3. 缓存与库之间不得出现「读到的更新、落库的没落上」这种静默分叉。

---

## 5 技术选型

| 类别 | 选型 | 说明 |
|---|---|---|
| 缓存 | Redis | 键值存储，承载实时最新状态 |
| 关系库 | MySQL | 历史与低频数据 |
| 访问层 | JPA 或 MyBatis-Plus | 与 M1、M4 保持一致 |

## 附录 A 术语

本文特有：

| 术语 | 含义 |
|---|---|
| 实时最新 | 只关心当前值、不需要回溯的那部分数据 |
| 活跃占位窗口 | 尚未释放的占位记录，供占位冲突即时判定 |
| 异步落库 | 写缓存成功后再写库，失败需补偿 |

通用术语引 `02-术语表`。
