## 1 模块定位与边界

M1 是系统的**数据源头**，是常驻层的地基——**不因订单启停、从开机起持续在线**。它以「连接器 → 解码器 → 发布器」三段式流水线，把五路外部原始数据接入、解析为结构化对象、投递到消息队列，供 M2 状态估计与预测、M3 路径规划、M4 监控、M5 可视化、M6 存储按需消费。

模块目标四条：

| 目标 | 含义 |
|---|---|
| 接得到 | 稳定接入五路数据源：AIS 船位、无人机遥测、气象、水文、航道与空域公告 |
| 解得出 | 把各源原始报文解析为统一结构化对象 |
| 送得到 | 投递到消息队列或共享数据源；**遥测只接入一次**，避免各模块重复接入、重复清洗 |
| 看得见 | 接入链路健康可观测（在线、断流、延迟） |

边界：

| 做 | 不做 |
|---|---|
| 五路接入、解析、格式级校验、投递 | 不做状态估计（去噪、去重、丢包外推）——归 M2 |
| 链路健康监控与告警 | 不做坐标与单位归一——归 M6 落库时完成 |
| 提供 MQTT 通道与编码适配 | 不判断「该不该发指令」——业务判断归 M4 |
| — | 不建业务表（`ship_ais`、`flight_point`、`alert` 等归 M6） |
| — | 不参与订单接入——订单归 M2 |

## 2 模块间关系

| 对接对象 | 方向 | 方式 | 交互内容 |
|---|---|---|---|
| 外部数据源（AIS 岸基或第三方、气象、水文、航道空域公告） | 输入 | TCP、UDP、HTTP | 原始报文与响应 |
| 无人机与机巢链路 | 双向 | MQTT（本模块建链） | 收：无人机遥测（位置、高度、速度、电量、航向），**由本模块接入并解码，全系统只接入一次**；发：飞行指令——**指令由 M4 判定与编码，经本模块已建立的 MQTT 通道下发**，本模块不判断「该不该发」 |
| M2 调度引擎 | 输出 | MQ | 结构化原始态势数据（供其状态估计与滚动预测） |
| M3 动态会面、路径规划 | 输出 | MQ、共享数据源 | 气象、水文与空域约束数据（禁飞区、限飞区、桥梁净空、限高等底图约束的来源）。**应急迫降点不在此列**——它是运营方预先登记的静态设施台账，由 M6 承载，非外部采集所得 |
| M4 飞行任务监控 | 输出 | MQ、共享数据源 | 无人机遥测（**已完成格式级校验**）。M4 不再自行接入与基本校验，其校验职责上移为飞行语义级（野值剔除、丢包外推） |
| M5 终端交互、可视化 | 输出 | MQ、共享数据源 | 实时船位、无人机位置 |
| M6 数据库、缓存 | 输出 | DB、Redis | 历史数据落 `ship_ais` 等表；实时最新状态写 Redis |

链路归属（已拍定，见 51 §2）：本模块即《模块调用链》待定项 #10 所指的「统一接入层」。**下行**由本模块统一接入并解码，全系统只接入一次，M4 不直连 MQTT；**上行**飞行指令由 M4 判定与编码，经本模块已建立的 MQTT 通道下发。「收发同源」仍成立（同一条 MQTT 链路），职责不重叠。

## 3 功能分解

5 个子模块，共 19 个功能点。优先级：★必做 ☆选做。

### 3.1 数据源接入子模块（连接器层）

| 编号 | 功能点 | 功能描述 | 实现要点 | 优先级 |
|---|---|---|---|---|
| 2.1.1 | AIS 船位数据接入 | 接入内河岸基或第三方 AIS 流的船位报文 | Netty TCP/UDP 客户端；支持多基站 | ★必做 |
| 2.1.2 | 无人机遥测接入 | 订阅 MQTT 主题接收无人机遥测（位置、高度、速度、电量、航向等） | Eclipse Paho MQTT；与 M4 §2.1.1 **同一条链路、同一份数据** | ★必做 |
| 2.1.3 | 气象数据接入 | 定时拉取江面气象（风速、风向、阵风等） | Spring WebClient 定时拉取 | ★必做 |
| 2.1.4 | 水文数据接入 | 定时拉取水位、流速等水文数据 | WebClient 定时拉取 | ★必做 |
| 2.1.5 | 航道与空域公告接入 | 拉取或抓取航道管制、空域限制公告 | HTTP、Jsoup 抓取 | ★必做 |
| 2.1.6 | 连接生命周期管理 | 心跳保活、断线自动重连、限流背压 | 退避重连策略 ＋ 令牌桶限流 | ★必做 |

### 3.2 协议解析子模块（解码器层）

| 编号 | 功能点 | 功能描述 | 实现要点 | 优先级 |
|---|---|---|---|---|
| 2.2.1 | AIS 报文解码 | AIVDM、NMEA 报文转 `AisMessage` | 6-bit ASCII 载荷与位段解析 | ★必做 |
| 2.2.2 | 无人机遥测解析 | 上云或 MAVLink 报文转 `UavTelemetry` | 字段映射（兼容 mavlink-java） | ★必做 |
| 2.2.3 | 气象与水文解析 | JSON、XML 转 `WeatherData`、`HydroData` | 字段映射 | ★必做 |
| 2.2.4 | 公告文本抽取 | HTML 或纯文本转 `AirspaceNotice` | 规则抽取（标题、区域、时间窗） | ☆选做 |
| 2.2.5 | 基本校验 | 经纬度范围、时间戳合理性校验 | 参数校验（深度去噪、去重、外推归 M2） | ★必做 |
| 2.2.6 | 解析异常处理 | 无法解析的坏包隔离并计数 | 死信记录，不影响主流程 | ★必做 |

解析层**只做「还原」，不做坐标与单位归一**，字段保持源原始单位与坐标系；归一由 M6 在落库、入缓存时统一完成（见 02-术语表 §5）。

## 4 关键设计

### 4.1 三段式流水线

```
连接器（接入）→ 解码器（解析）→ 发布器（投递）
五路数据源        统一结构化对象      消息队列、共享数据源
```

流水线的接口边界：连接器一收到原始数据就回调 `onRaw(RawPayload)`，出错回调 `onError`——这是采集层与解析层之间的边界接口（`RawDataHandler`）。新增数据源时只实现连接器与解码器，不改主流程。

### 4.2 清洗三级分层

同一份数据在三处各清洗一次，不许重复：

| 层级 | 内容 | 承担方 |
|---|---|---|
| 格式级 | 字段范围、时间戳合理性、基本去重 | **M1**（本模块） |
| 船舶状态估计 | 去噪、去重、丢包外推 | M2 |
| 飞行语义级 | 野值剔除、短时丢包外推 | M4 |

### 4.3 全系统只接入一次

无人机遥测由本模块**接入、解码、完成格式级校验后发 MQ 交付 M4**；**共享数据源由 M4 在飞行语义级清洗后写入**（U-03 裁决，2026-10-08，M1 回执已确认）。**本模块不产生对共享数据源的写操作**，共享数据源对本模块为只读消费。这样 M3 纠偏所需的实时遥测不需要为「M4 到 M3」单独定义通道——它不再是模块间直连，而是共享数据（由 M4 写入）。

**数据流终稿**：`机载遥测 → 接入 → 解码 → 格式级校验 → 发 MQ → M4 → 飞行语义级清洗 → 写入共享数据源`。

> 原表述「由本模块接入并解码后写入共享数据源」已作废（U-03）。另：§2 目标「投递到消息队列或共享数据源」、§3 模块间关系中「M3／M5 经共享数据源」两项仅针对**气象、水文、空域公告、实时船位**等非遥测数据；遥测一律按上条走 MQ。**气象等非遥测数据是否亦须经 M4 写入共享数据源，待 M1 与 M4 确认**（U-03 裁决范围原为遥测）。

### 4.4 归一归属

坐标与单位归一**不在本模块**：本模块保持源原始单位与坐标系交付，M6 落库与入缓存时统一到基准坐标系（CGCS2000 / WGS84）与标准单位，下游一律从 M6 取标准值。原因：M3 算航迹、M5 画地图都要用坐标，若各模块各持一套原始坐标自行转换，误差与不一致不可避免；国内坐标系还存在 GCJ02、BD09 的偏移问题，必须由单一环节统一。

## 5 数据读写需求

本模块**不建业务表**，只投递：

| 产出 | 去向 |
|---|---|
| 解析后对象（`AisMessage` 等） | MQ 主题 `data.*`，供 M2、M3、M4、M5 消费 |
| 历史数据 | 由 M6 落 `ship_ais`、`weather`、`hydro`、`airspace_restriction` 等表 |
| 实时最新状态 | 由 M6 写 Redis |
| 接入健康 | `ConnectorHealth` 暴露给运维与可视化 |

表结构以 `37-M6-数据库` 为准。

## 6 技术选型

| 类别 | 选型 | 理由 |
|---|---|---|
| 后端框架 | Spring Boot 3.x | 与 M4 一致 |
| AIS 接入 | Netty | TCP、UDP 长连接、自定义编解码 |
| 无人机遥测与消息 | Eclipse Paho MQTT、Mosquitto | 与 M4 一致，同一条 MQTT 链路 |
| 气象与水文接入 | Spring WebClient | HTTP 定时拉取 |
| 公告抓取 | Jsoup | 页面与文本抽取 |
| 消息队列 | RabbitMQ、Mosquitto MQTT | 与 M4 一致，模块间解耦 |
| 数据库与缓存 | MySQL（历史）、Redis（实时最新） | 由 M6 承载，本模块只投递 |
| 仿真环境 | PX4 SITL ＋ jMAVSim | 无实物时输出真实飞控遥测供联调 |
| 构建工具 | Maven | Java 项目标准构建 |

## 附录 A 术语

本文特有：

| 术语 | 含义 |
|---|---|
| 连接器 | 与某一路外部数据源建链并持续接收原始数据的组件 |
| 解码器 | 把某源原始报文还原为统一结构化对象的组件 |
| 发布器 | 把解析结果封装并投递到消息队列的组件 |
| 格式级校验 | 字段范围、时间戳合理性、基本去重，与飞行语义级清洗区分 |
| 共享数据源 | 清洗后的状态供多模块按需取用的中间存储，避免点对点通道 |

通用术语（模块编号、系统服务航段、应急迫降点等）引 `02-术语表`。

## 附录 B 实现结构

基础包：`com.waterlogistics.collector`

| 层 | 接口与核心类 | 各源实现类 | 支撑类 |
|---|---|---|---|
| 连接器（接入） | `DataSourceConnector`、`ConnectionManager`、`RawDataHandler` | `AisConnector`、`UavTelemetryConnector`、`WeatherConnector`、`HydroConnector`、`NoticeConnector` | `DefaultConnectionManager`、`ConnectionRegistry`、`ReconnectPolicy`、`RateLimiter`、`SourceConfig`、`SourceConfigLoader`、`ConnectorState` |
| 解码器（解析） | `Decoder<R,T>`、`TelemetryDecoder` | `AivdmDecoder`、`UavTelemetryDecoder`、`WeatherDecoder`、`HydroDecoder`、`NoticeParser` | `AivdmBitUtils`、`DecodeFailureCollector`、`DecodeException` |
| 发布器（投递） | `DataPublisher`、`DeadLetterHandler` | `MqDataPublisher` | `RetryablePublisher`、`MessageEnvelopeFactory` |
| 调度与配置 | `CollectionScheduler` | `DefaultCollectionScheduler` | `CollectionPolicy` |
| 契约（model） | — | — | `RawPayload`、`SourceType`、`ParsedMessage`、`AisMessage`、`UavTelemetry`、`WeatherData`、`HydroData`、`AirspaceNotice` |

命名规则：接口不加 `I` 前缀；实现类用具体名（`AisConnector`）或技术前缀（`MqDataPublisher`）；枚举用单数（`SourceType`）；异常以 `Exception` 结尾。

**类名冲突的裁决**（见 51 §2、决议 C3）：以 M1 功能细化 §5 为基准，`UavTelemetryDecoder`、`NoticeParser`、`MqDataPublisher`、`AirspaceNotice` 为准；早期任务拆分里的 `UavTelemetryJsonDecoder`、`NoticeTextParser`、`KafkaDataPublisher`、`Notice` 一律废弃。其中 `KafkaDataPublisher` 还因技术选型冲突废弃——全项目的 MQ 基调是 MQTT 与 RabbitMQ，不引入 Kafka。
