## 1 结论

场景要展示的四件事——按机型抗风淘汰候选、会面点吃风、风速越限停派、越限后弃会面返航——**公式都在，断的是接线**。v2 的方向对，但按 v2 的清单做完，其「场景回放」验收仍跑不通。

| 场景能力 | 现状（`fb48411` 核实） | 处置 |
|---|---|---|
| 会面点吃风 | `EffectiveSpeed` 已实现 `v = cruise − wind·cosΔ`；`representativeWind()` 读 `windSpeedMs`、缺省 0，且 `data.weather` 无消费者 | 接气象快照 |
| 可行风闸 | `FeasibilityJudge` 判据在，但**主链无调用方**（`CandidateService.generateAndJudge` 无人调） | 判定入链 |
| 机型差异 | `drone` 只有载重/续航/电量，无巡航速度与抗风上限；`CandidateCombo`、`CandidateInput.DroneView` 均无该字段 | 加 2 列并贯通候选链 |
| 派单闸门 | `DispatchGateService` 有 `trip/clear/summary`，`isOpen()` **无生产调用方** | 接到受理与组批 |
| 在飞弃会面 | `abandonMeetAndReturnHome`／`requeueOrder` **只有单测在调**，无生产触发方 | 接在飞复核（P0-7） |
| 气象消费 | M1 在发 `data.weather`，`WeatherData` 已是契约 record；**全项目零消费者** | M2 新增监听 |
| 气象超限事件 | 有 `AlertType.WEATHER_EXCEED`，**无检测器、M4 无监听** | P1-4（拍板 3） |
| 参数登记 | `SysParamBridge` 已按 17 键读取并兜底，其中 16 键未灌库；`002` 第 101 行**残留 `<<<<<<< HEAD`** | 先修文件再灌键 |
| 机巢/桥梁/机型数据 | `nest.lon/lat`、`airspace_restriction.scope` 可承载；`drone` 三行未配 | 灌数据 |
| 风速突变源 | 仿真器基准 5±1.5 m/s，**永远够不到 8/12 阈值**，且无注入入口 | 加注入端点 |
| 仿真几何 | AIS/气象默认在武汉（114.30, 30.60），不是赣江 | 后端演示前切坐标 |

**改动总量**：DDL 2 列；代码约 18 个文件（新增 6 个类）；`sys_param` 新增 22 键、复用登记 2 键；新增 2 个 MQ 监听、4 处接线（闸门、可行性、在飞复核、回收重入队）、2 个仿真端点。

### P0-1　机型能力入表，并沿**候选链**传到判定

| 环节 | 改什么 |
|---|---|
| 表 | `001_init.sql` `drone` 增 `cruise_speed`、`wind_limit`（DECIMAL(6,2)）；`DroneEntity` 同步 |
| 候选输入 | `CandidateInput.DroneView` 增 `cruiseSpeedMs`、`windLimitMs`；`CandidateSelector.buildInput` 从实体填 |
| 候选记录 | `CandidateGenerator.CandidateCombo` 增同名字段，`generate()` 时拷贝 |
| 判定 | `FeasibilityJudge.judge` 用 `combo.windLimitMs()` 比对；≤0 时回落 `Params.maxWindMs`，既有单测不破 |
| 会面求解 | `DroneContextAdapter.resolve` 的巡航速度改为「实体列优先、`sys_param.droneCruiseSpeedMs` 兜底」 |
| 测试 | `FeasibilityJudgeTest` 补「同风速下 A 淘汰、B 保留」1 例 |

**关键**：`DroneContextAdapter` 只服务 M3 会面重算，**不在候选链上**（v2 在此写错）。三架机的能力差异必须在 `CandidateCombo` 可见，否则风闸恒真、会面同速。

**字段归属**：抗风上限与巡航速度是机型属性，首版落在 `drone` 实例表，文档注明「按实例冗余，正式版拆机型档案」，不新建表。

### P0-3　气象 → 闸门（M2 消费 `data.weather`）

- 新增 `dispatch/gate/WeatherGateListener`，按 `AisIngestListener` 的写法声明独立队列 `wavenest.m2.data-weather`（与 M4 将来的气象队列分开，避免竞争消费）。
- 触发：单条 `windSpeedMs ≥ weatherFuseThreshold` 即 `trip(GateSource.AUTO)`——首版取保守口径（任一网格点越阈即停派）。
- 恢复：连续 `weatherFuseClearDebounce` 条全部低于 `weatherFuseThreshold × 0.9` 后 `clear(GateSource.AUTO)`；人工解除仍走 `MANUAL`。
- 边界：**闸门只管新派单**；在飞复核走 P0-7，两者在同一监听入口分流，不互相替代。M2 只比较风速量，不判级、不产告警，检测与判级仍归 M4。

### P0-4　闸门真正生效（v2 漏项）

现状 `isOpen()` 无人调用，只加监听器不会产生任何行为。改两处：

| 位置 | 行为 |
|---|---|
| `OrderAdmissionService.submit` | 闸门关：受理后直接置「已受理待唤醒」＋`waitReason=GATE_OR_DATA`；闸门开：原路径 |
| `TaskQueueService.startDispatch` | 再查一次，防「组批窗口内刚熔断」，关则退回待唤醒 |

依据：`21` §2「熔断期间只受理不派单」；`WaitReason.GATE_OR_DATA` 已存在，枚举零改动。

**注意**：`TaskQueueService.accept` 目前只有冒烟测试在调，REST 下单只建内存 `OrderView`、不落 `order_task`。因此闸门检查应挂在**接收入口**；场景要跑到派发，需在 P2-1 的固定输入入口里显式建单（该持久化缺口不在本方案范围，见风险）。

### P0-5　可行性判定入链（v2 漏项）

`CandidateSelector.selectBest` 生成候选后逐个 `judge()`，在**可行**者中按距离取最优；全部不可行返回 `null` 并记淘汰原因。
所需最不利风速由 P1-1 的 `WeatherSnapshotPort` 提供，与闸门共用一次取数。

### P0-6　闸门摘要回显

`OrderController` 注入 `DispatchGateService`，回 `summary()`，删除硬编码「正常」（该类注释已标「临时实现」）。

### P0-7　在飞复核与重入队接线（v2 漏项，场景主故事缺这一段）

`abandonMeetAndReturnHome` 与 `requeueOrder` 目前**只有单测在调**，没有任何生产触发方；不接这段，场景的「风速超限 → 弃会面 → 携货返航 → 回收 → 重入队」无法发生。

| 环节 | 改什么 |
|---|---|
| 触发 | 与 P0-3 共用一个监听入口：先按各在飞机的 `wind_limit` 逐机判、再按 `weatherFuseThreshold` 判停派，两条线互不替代 |
| 复核 | 对在飞任务（`order_task.status` ∈ 已派发/去程中/末段交接中）组装 `HomecomingInput`（电量、位置、归属巢、载货）＋ `HomecomingParams`（`e10*` 键按 `84` §4.3.1 换算）＋ 候选他巢，调 `RescheduleService.abandonMeetAndReturnHome` |
| 落点 | 回原巢 → 返航指令交 M4（`HomecomingService` 现有 TODO 三处按需接实）；迫停他巢 → 发占位请求；迫降野外 → 转人工 |
| 回收 | 落巢＋回收确认后调 `requeueOrder`；确认位首版由仿真端点 `POST /sim/task/landed?orderId=` 置位（与 P1-3 同一风格），不伪造 |
| 边界 | **不改 6b 判据**、不做空中换机；弃会面后订单只是回到「待调度」，是否重新派发仍由闸门与候选决定 |

**DoD**：固定输入测试走通「越阈 → 弃会面 → 三级落点 → 落地回收 → 重入队（待调度）」。

### P1-1　代表风况接气象快照

1. M2 声明端口 `WeatherSnapshotPort`（与 `TrajectorySnapshotPort` 同风格）：`latest()` 返回风向、风速、观测时刻；`latestWorstWindMs()` 返回最新观测周期内全网格最大值；

### P1-3　风速突变注入（v2 漏项）

无注入手段，场景的「一次风速突变」只能靠改代码重跑。仿 `TurnInjectController` 加 `POST /sim/weather/surge?wind=14&holdSec=60&delaySec=0`，`SimWeatherConnector` 支持覆盖值并可 `reset`；注入需可复现、可计时。

### P1-4　M4 气象超限检测（按拍板 3，可砍）

`34-M4` §3.4 与 `AlertType.WEATHER_EXCEED` 都已在，缺实现：新增 `WeatherDetector`（绝对阈值＋突变率，读 `SysParamProvider` 五个气象键）＋ M4 的 `data.weather` 监听，产 `alert_type=气象超限` 并推 `alert.event`、写 `alert` 表。

## 3 明确不改

- **算法公式**：`RendezvousSolver`、`EffectiveSpeed`、`FeasibilityJudge` 判据形式、`IntentChangeJudge`、`HandoverJudge`、检测双阈值与迟滞、预测层。
- **契约**：`AlertType`/`GateStatus`/`GateSource`/`TaskStatus`/`OrderStatus`/`WaitReason` 零改动。
- **表**：除 `drone` 两列外不动，不为桥梁/机巢新建表。
- **状态机与 MQ**：任务六态与异常分支不动；订单只用 `23` §3 既有路径（闸门分支走 `待受理 → 已受理待唤醒`，不新增状态）；主题与消息结构不动。
- **6b**：判据代码保持现状，场景不验证它；P0-7 只接气象触发的弃会面路径，不复用 6b。

## 6 验收（四层，别混）

1. **参数一致**：代码读取键名 ＝ `002` 灌入键名 ＝ `37` §5.14.1 登记键名，同一份 grep 清单核对。
2. **单测**：①风速超 A 机上限、未超 B 机 → A 淘汰 B 保留；②越阈 trip、回落且防抖满足 clear；③熔断中 `accept` 转待唤醒、`startDispatch` 被拒；④会面点随风速变化而变化；⑤候选记录携带逐机速度与抗风上限。
3. **链路**：固定输入跑通「下单 → 候选 → 会面 → 派发 → 风速超限 → 停派 → P0-7 弃会面 → 携货返航 → 回收 → 重入队（待调度）→ 风未恢复不派发」。
4. **对外口径**：净空数据未补齐不称已验证净空；Unity 未对照不称结果一致；第 3 项未做不称「监控侧产生事件」。

## 7 风险

- `002` 的冲突标记不清，D1 起所有灌库验证都不可信。
- 下单只建内存视图、不落 `order_task`，`accept` 也仅测试在用；不先补建单入口，闸门与在飞复核都无对象可查。
- `drone` 两列为 `NULL` 时必须显式回落全局值，否则演示会「静默用 10 m/s」。
- 新增气象监听器务必用独立队列；与 M4 同名队列会变成竞争消费、两边都收不全。
- 仿真器不切到赣江坐标，后端直播演示的空间关系就对不上场景，只能作为冒烟链。
