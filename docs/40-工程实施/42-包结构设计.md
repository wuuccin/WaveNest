> 设计原则：**隔离**（模块边界＝Gradle 模块边界，物理隔离）、**可拓展**（换数据源／加算法／拆部署不改骨架）、**低耦合高内聚**（模块间只走契约，算法纯计算）。
> 服从库内既有裁决：基础包 `com.waterlogistics`（`30-M1` 附录 B 已定 `com.waterlogistics.collector`）；依赖方向照 `20-系统架构` §3（M2 唯一调度主控、M6 纯基础设施、闭环只经 M2 闭合）；U-01（纠偏循环体在模块三侧）、U-03（模块一解码后发 MQ 交付模块四写共享数据源）。

## 1 总体形态（monorepo）

```
wavenest/
├── docs/                      # 项目共有文档（契约 22／状态机 23／表结构 37…，整库进仓）
├── deploy/                    # docker-compose.yml、建库 DDL、离线瓦片包
├── backend/                   # 后端（Gradle 多模块，JDK 17+ ／ Spring Boot 4.1.x）
│   ├── wl-common/             # 通用底座：工具、统一异常、Result 封装
│   ├── wl-contract/           # ★ 契约唯一权威：22 的 MQ／REST／WS 对象 ＋ 23 状态枚举 ＋ 主题名常量
│   ├── wl-algo/               # ★ 算法层：A–G 七组纯计算，无 Spring、无 DB
│   ├── wl-storage/            # 模块六 数据库与缓存：14 表实体、Repository、Redis、sys_param
│   ├── wl-m1-collector/       # 模块一 数据采集（含仿真器）
│   ├── wl-m2-dispatch/        # 模块二 调度引擎
│   ├── wl-m3-rendezvous/      # 模块三 动态会面与路径规划
│   ├── wl-m4-monitor/         # 模块四 飞行任务监控
│   └── wl-app/                # 组装层：SpringBootApplication ＋ application.yml ＋ push/（后端唯一实时出口）
├── frontend/                  # 模块五 终端交互与可视化（Vue3 ＋ Vite 8 ＋ pnpm）
└── scripts/                   # 冒烟脚本、演示脚本、一键演示
```

**为什么是这 9 个模块**：每个 Gradle 模块＝一个职责边界＝一个可独立编译／单测的单元；`wl-app` 只做组装不含业务，演示期起一个进程，将来拆多进程部署时按 Gradle 边界拆走、**业务代码零改动**——这是「隔离」的物理保证。`wl-app` 之下另含 `push/`——后端**唯一**的实时（WS／SSE）出口，与前端 `realtime/` 一一对称；它无业务判断、只是帧的扇出口，故不单立模块。

## 2 依赖方向（铁律，单向无环）

```
wl-app ──→ m1 / m2 / m3 / m4
wl-app.push ──→ 前端（WS/SSE，唯一实时出口）
m1~m4  ──→ wl-algo、wl-storage、wl-contract
m2     ──→ m3（唯一例外：经 m3 对外 facade 同步调用会面求解／航迹生成，31 §6 硬约束）
wl-algo / wl-storage ──→ wl-contract ──→ wl-common
```

1. **模块间禁止 import 对方内部类**。运行期通信只走契约（MQ 主题／REST／WS，对象全部来自 `wl-contract`，照 `22`）。
2. **M2→M3 是唯一允许的编译期跨模块调用**，且只能调 m3 的 facade（`RendezvousFacade`），m3 **不反向依赖 m2**。
3. **M3 需要船侧预测快照**（L-7 裁决）：用**端口反转**——m3 自己声明 `TrajectorySnapshotPort` 接口，m2 提供实现，`wl-app` 装配时接线。m3 全程不知道 m2 存在。
4. **wl-algo 不依赖 Spring Boot／MQ／storage**：纯 Java 计算，输入输出对象自带，阈值与台账参数由调用方注入（`33` §6 硬约束 2：禁飞区约束来自台账、不硬编码）。算法可脱离全项目独立单测。
5. **一套实现两种触发**（`20` §2 硬约束 3）：常驻滚动预测与接单精算预测共用 `wl-algo` 同一实现，模块二只做两种触发编排，**禁止两套代码**。
6. **前端只有一个实时入口**：`wl-app.push` 是后端**唯一**的 WS／SSE 出口，各模块产帧后交给它扇出（已有 MQ 主题者如 `alert.event`／`data.*` 直接订阅，无主题者如 `order_state` 走进程内端口投递），帧字段照 `22` §4。**任何模块都不得自开 socket 直连前端**；`wl-app.push` 与前端 `realtime/` 一一对称（同一套信封与降级顺序）。

## 3 各模块内部包结构（按分工表拆到人）

### 3.1 wl-m1-collector —— `com.waterlogistics.collector`（杨添爻，照 `30` 附录 B 原表不改）

```
collector/
├── connector/    # DataSourceConnector SPI ＋ AisConnector、UavTelemetryConnector、
│                 #   WeatherConnector、HydroConnector、NoticeConnector
├── simulator/    # ★ 仿真器＝连接器的一个实现：SimAisConnector、SimWeatherConnector、
│                 #   变向注入开关（REST 触发）。换真实源时只换实现类，下游零改动
├── decoder/      # Decoder<R,T>、AivdmDecoder、UavTelemetryDecoder…
├── publisher/    # DataPublisher、MqDataPublisher、MessageEnvelopeFactory
├── scheduler/    # CollectionScheduler
└── model/        # RawPayload、AisMessage、UavTelemetry…（照附录 B 契约层）
```

命名规则照 `30` 附录 B：接口不加 `I` 前缀；实现类用具体名（`AisConnector`）或技术前缀（`MqDataPublisher`）；枚举单数；异常以 `Exception` 结尾。

### 3.2 wl-m2-dispatch —— `com.waterlogistics.dispatch`（卢肄文／张睿哲／吴可欣三人，子包＝分工边界）

```
dispatch/
├── order/         # 订单接入与基本校验（卢）
├── prediction/    # 船舶状态估计与轨迹预测管理（卢）：常驻滚动 ＋ 接单快照两种触发，
│                  #   统一调 algo.estimation；预测快照同时实现 m3 的 TrajectorySnapshotPort
├── record/        # 调度结果记录与展示（卢）：写 task_log 事件流
├── candidate/     # 候选机型／机巢／无人机生成、候选组合可行性判断（杨添爻）：调 algo.candidate
├── selection/     # 候选方案综合择优（张）：调 algo.selection
├── resource/      # 资源占用与并发冲突管理（张）：占位时隙台账
├── confirm/       # 航线确认与起飞时刻确定（张）
├── queue/         # 任务队列与状态管理（张）：照 23 状态机推进
├── gate/          # 派单闸门与人工干预（张）：gateStatus/gateSources 回显、/api/intervene
├── reschedule/    # ★ 飞行过程中的重新调度（吴）：意图变更判据入口→放弃会面→订单重入队
└── homecoming/    # 返航复核与归巢资源判定（吴）：调 algo.inflight 三级判定
```

### 3.3 wl-m3-rendezvous —— `com.waterlogistics.rendezvous`（罗才辉为主）

```
rendezvous/
├── facade/       # RendezvousFacade：对 m2 唯一暴露的同步入口（会面求解／航迹生成按组合循环调用）
├── solver/       # ★ 会面点求解（罗）：调 algo.meeting【本轮真算法 1】
├── trajectory/   # 可飞航迹生成、返航航迹生成、起飞时刻回填（罗）
├── conflict/     # 航迹级空域冲突二查（罗）
├── handover/     # 末段会面与交接（罗）
├── correction/   # ★ 去程段追踪与纠偏循环体（吴／罗，U-01：循环体在本模块侧、
│                 #   「每收到一次新状态」触发；判据调 algo.inflight）
├── deviation/    # 会面偏差回流（宋）：入＝本模块末段交接完成确认（m3.handover 产出的计划／实际
│                 #   会面点与时刻，86 §1.2），出＝发 MQ 回 M2（22 §5 数据回流行）；只产偏差样本与
│                 #   分层统计量、不写 sys_param，不直调 correction
└── port/         # TrajectorySnapshotPort（预测快照端口声明，m2 实现，app 接线）
```

### 3.4 wl-m4-monitor —— `com.waterlogistics.monitor`（彭紫情／宋冰鑫／吴可欣三人）

```
monitor/
├── ingest/       # 遥测数据接收、航线数据获取、数据校验过滤（彭）；U-03：共享数据源由本模块写
├── track/        # 偏航距离计算、飞行进度定位、剩余航程估算（彭）
├── query/        # 任务列表与查询（彭）
├── store/        # 飞行数据记录、历史轨迹回放、飞行统计（彭）：供回放模式
├── taskstate/    # 任务状态流转、进度与 ETA 计算、投送确认（吴）
├── detect/       # 航线偏离检测、低电量预警、失联检测、气象超限（宋）：调 algo.detection，
│                 #   阈值全部读 sys_param
└── alert/        # 告警记录与投递（宋）：写 `alert` 表、发 `alert.event`（MQ，22 §1.2），帧交
                  #   `push/` 出口推 WS；只检测不决策（20 §3）
```

### 3.5 wl-storage —— `com.waterlogistics.storage`（张睿哲，模块六 16 项）

```
storage/
├── entity/       # 14 张表实体（照 37 §5.1–§5.14 一字不改；坐标与单位归一照 §6）
├── repository/   # Repository ＋ 归一处理单元
├── cache/        # Redis 读写策略（照 38）：实时最新状态、预测快照缓存
└── param/        # sys_param 集中加载（§5.14.1 全量键）：唯一定值入口，业务方只读不硬编码
```

约束：**M6 不做业务判断**（`20` §3），只保证「写得对、读得一致、可追溯」。

### 3.6 wl-algo —— `com.waterlogistics.algo`（A–G 七组，纯计算）

```
algo/
├── estimation/   # A组·船舶状态估计与轨迹预测（卢）：滤波、多步预测、不确定性带
├── meeting/      # B组·动态会面与航迹（罗）：会面点求解【本轮真算法】、航迹推演
├── candidate/    # C组·候选与两关剪枝（杨）
├── selection/    # D组·择优与占位并发（张）
├── inflight/     # E组·飞行中追踪与返航（吴）：滑窗航向差、意图变更判据 6b【本轮真算法】、
│                 #   返航复核三级判定
├── measurement/  # F组·量测与状态（彭）：只产量不判级（量判分离）
└── detection/    # G组·检测与判级＋会面偏差回流（宋）：判级只归本组；偏差回流只产样本与统计量（86 §1）
```

**组间铁律（「量判分离」的精确边界，勿越界）**：`measurement/` 是**机侧量**的唯一生产方——无人机的偏航距离、飞行进度、剩余航程等，判级一律由 `detection/` 消费这些量后完成，这就是「F 产量、G 判级」那一对。`inflight/` 自产的**船侧**偏差特征（预测—实测 XTE 走廊、滑窗平均航向差，`84` §2.1／§2.5）与前者**同名不同物**（量的是船、不是机），不属 `measurement/` 的量清单，由本组自产自用；两组不得互抢，也不得替对方实现同名量。

### 3.7 wl-contract —— `com.waterlogistics.contract`（收口方维护，全组只读）

```
contract/
├── mq/           # MQ 消息对象 ＋ TopicName 常量（照 22 §1/§2）。闭环与推送主题**均已有出处**：
│                 #   `alert.event`＝M4 告警（M4→M2／M5，22 §1.2）、`task.plan`＝M2→M4（含船舶预测轨迹）
├── rest/         # REST 请求／响应对象 ＋ 路径常量（照 22 §3，含 /api/intervene）
├── ws/           # WS 帧对象与统一信封（照 22 §4：ship_traj、order_state、alert…）
└── state/        # 四套状态机枚举：订单／任务／货物／无人机（照 23，全组唯一）
```

**纪律落点**：字段只从 `22`／`37`／`23` 复制进本模块；全组发现契约缺口报组长，不改本模块。

### 3.8 wl-app —— `com.waterlogistics.app`（收口方）

只含启动类、`application.yml`（MQ／Redis／MySQL 连接、仿真 profile）、Bean 装配（端口接线：`TrajectorySnapshotPort` ← m2 实现）。**不含任何业务逻辑**。

```
app/
└── push/         # ★ 后端唯一实时出口（彭）：WS／SSE 服务端 ＋ 帧扇出。帧料来自 M2／M4
                  #   （已有 MQ 主题者直接订阅，`order_state` 等无主题的帧经进程内端口投递），
                  #   按 22 §4 五类帧广播给前端；纯转发、无业务判断
```

**为什么 `push/` 在 wl-app 而不在 wl-m4-monitor**（对评审 Q1 落点的修正）：`22` §4 明写 `order_state` 写入方是 **M2**、`31` §2 也是 M2→M5 出订单进度，而 `22` §1.2 主题表里**没有** M2→M4 的订单态主题——出口若放 m4，就得凭空造一条只存在于实现里的 M2→M4 私路。放到组装层，M2／M4 各自产帧、共用同一出口，**模块层「谁产什么帧」的口径一个字都不用动**（`34` §2「M4 → M5 WebSocket」在实现层即由此承载）。

## 4 前端结构（frontend，彭紫情，Vue3 ＋ Vite 8 ＋ Pinia ＋ Leaflet ＋ ECharts）

```
frontend/src/
├── api/          # REST 客户端（照 22 §3 四接口）：唯一后端 REST 出口
├── realtime/     # WS→SSE→轮询三级降级封装（照 36）：唯一实时数据出口（与后端 `wl-app.push` 对称）
├── stores/       # Pinia：ship / drone / order / alert / event / weather——唯一数据枢纽
├── layers/       # 大屏五图层（照 36 §3）：shipLayer、meetingLayer（十字准星）、
│                 #   droneTrackLayer（三段着色）、alertLayer（红闪）、statsPanel
├── views/        # dashboard 大屏 / console 人工干预台 / replay 回放
├── components/   # 通用组件：订单状态时间线、事件流、图例
└── styles/
```

**隔离规则**：图层组件**只订阅 store、不互相 import**、不发请求；后端字段变动只改 `api`／`realtime` 两处；一键演示＝`views/dashboard` 内的编排器依次调 `api` 触发，不新开后门。

**依赖与版本**：包管理器固定 **pnpm**——版本写在 `frontend/package.json` 的 `packageManager` 字段，由 Node 自带 corepack 自动切换（对应后端「Wrapper 锁版本」的同一条纪律）；仓库**只提交 `pnpm-lock.yaml`**，**禁止在仓库里跑 `npm install` 或 `yarn`**（会生成第二套锁文件、`node_modules` 结构也不同，联调必炸）。Vite 锁 major 8（当前 8.3.4）、Vue 3.5、Pinia、Leaflet、ECharts 6，精确版本由锁文件定格。

## 5 可拓展性落点（将来怎么长）

| 将来的需求 | 现在结构里的接口 |
|---|---|
| 接真实 AIS／气象源 | 新写 `AisConnector`／`WeatherConnector` 真实现，删 Sim 实现，下游零改动 |
| 算法从简化升精算 | 只改 `wl-algo` 对应子包内部，模块层 facade 与契约不动 |
| 单进程拆多进程部署 | 按 Gradle 模块拆 `wl-app` 为多个启动器，业务代码零改动 |
| 前端加船员端 H5 | `views` 加页面，复用 `stores`／`layers` |
| 新增告警类型 | `algo.detection` 加判定 ＋ `contract.ws` 加帧，monitor.alert 通用链路与 `app.push` 出口不动 |
| 换 WS 为 SSE／改推送协议 | 只改 `wl-app.push`（协议出口）与前端 `realtime`，各模块零改动 |
