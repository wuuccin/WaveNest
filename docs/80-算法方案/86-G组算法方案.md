## 1 功能 19 会面偏差回流

### 1.1 研究范围

| 项     | 内容                        |
| ----- | ------------------------- |
| 序号    | 19                        |
| 功能名   | 会面偏差回流                    |
| 所属模块  | M3                        |
| 需求条目  | M3-08（落点 32 §3.6）         |
| 回答的问题 | 实际会面偏差如何反哺，校准纠偏阈值与预测模型参数？ |

本功能是数据回流闭环的三项之一（见 21 §9）。另两项为：实际能耗→能耗模型动态权重；轨迹预测误差→预测模型参数。本文只覆盖「实际会面偏差→纠偏阈值与策略偏好」这一支，能耗与轨迹预测误差的校准归 M2 调度引擎相关算法。

### 1.2 输入与输出

**输入**（来自 M3 末段交接完成确认，见 22 §5 数据回流、22 §6 末段收尾、32 §3.6）：

| 输入项        | 来源                                   | 表示方式                       | 粒度        |
| ---------- | ------------------------------------ | -------------------------- | --------- |
| 计划会面点      | M2 任务方案下发的会面点经纬度                     | 经纬度（CGCS2000 / WGS84，十进制度） | 单值，每次任务一个 |
| 实际会面点      | M3 末段交接判定时记录的无人机与船实际相遇位置，交接完成确认时一并回流 | 经纬度（同上）                    | 单值，每次任务一个 |
| 交接完成时刻     | M3 交接完成确认的时间戳                        | 绝对时间戳                      | 单值，每次任务一个 |
| 计划会面时刻     | M2 任务方案中的会面时间窗中点                     | 绝对时间戳                      | 单值，每次任务一个 |
| 无人机 / 订单标识 | 任务方案                                 | `droneId`、`orderId`        | 单值，每次任务一个 |

**输出**（回喂 M2，见 22 §5 数据回流行）：

| 输出项                   | 去向                                           | 用途                                                                          |
| --------------------- | -------------------------------------------- | --------------------------------------------------------------------------- |
| 空间偏差（实际会面点 − 计划会面点）   | **E 组功能 17（纠偏阈值标定）** / **A 组功能 2（预测模型参数标定）** | 提供偏差样本与分层统计量 ＋ 校准建议；**本功能不写 `sys_param`**（跨组裁决 G-1）                         |
| 时间偏差（实际交接时刻 − 计划会面时刻） | M2（只作事实回流）                                   | 校准会面时间窗估算；**只产出偏差样本与分层统计量，由 B／D 自行决定是否吸收**，本功能不产出「起飞时刻回填修正量」这一动作量（跨组裁决 G-8） |
| 偏差样本元数据（机型、机巢、风况、船速段） | M2                                           | 按维度分层统计，避免不同条件下的偏差互相稀释                                                      |

**边界（明确不做什么）**：

- 不直接修改 `sys_param` 中的阈值。回流只提供统计样本与校准建议，阈值更新由 M2 决策侧统一发起，经 `sys_param` 写入（保证参数集中管理）。
- 不参与能耗模型与轨迹预测模型的校准（那两项由 M2 侧算法处理，本功能只交付偏差样本）。
- 不对单次偏差做即时阈值调整，避免抖动；校准基于滑动窗口内的统计量。

### 1.3 算法设计

**选了什么做法、为什么选**：

采用「滑动窗口统计 ＋ 偏差分解 ＋ 分层校准」的做法。理由：

1. 单次会面偏差受瞬时风况、船速抖动、飞控跟随误差等随机因素影响，直接拿单次值调阈值会导致阈值来回抖动、稳定性差。滑动窗口取统计量（均值、标准差、分位数）才能分离系统性偏差与随机噪声。
2. 偏差需要分解为**空间偏差**（位置维度）与**时间偏差**（时刻维度）。空间偏差反映纠偏阈值是否过松或过紧；时间偏差反映会面时间窗的估算是否偏乐观或偏保守。两者校准的对象不同，必须分开。
3. 不同条件下偏差分布不同（大风天 vs 小风天、快船 vs 慢船、不同机型），混在一起统计会相互抵消。需按机型、风况段、船速段分层，每层独立统计。

**核心思路与步骤**：

1. **采样**：每次交接完成，M3 记录「计划会面点、实际会面点、计划会面时刻、实际交接时刻」四元组，连同机型、机巢、当前风况、船速段等上下文，构成一条偏差样本，写入回流队列（见 22 §5 数据回流）。
2. **偏差计算**：
   - 空间偏差 `d_space = Haversine(实际会面点, 计划会面点)`，单位米。
   - 时间偏差 `d_time = 实际交接时刻 − 计划会面时刻`，单位秒；**仅作为时间维度偏差的统计量输入，不生成任何动作量**（G-8 已定）。
3. **滑动窗口聚合**：维护最近 N 条样本的滑动窗口（窗口大小 N 为参数），按机型 × 风况段 × 船速段分层，每层分别计算：
   - 空间偏差均值 `μ_space`、标准差 `σ_space`、95 分位数 `p95_space`；
   - 时间偏差均值 `μ_time`、标准差 `σ_time`。
4. **偏差统计量与校准建议生成**：
   - 纠偏阈值校准建议（仅针对空间偏差）：若 `μ_space` 持续偏大于当前纠偏容忍阈值的一定比例（说明预测系统性偏慢，会面点偏后），建议收紧纠偏阈值或调整会面策略偏好；若 `p95_space` 远小于当前阈值（说明阈值过松，频繁下发无意义指令），建议放宽阈值。
   - 时间偏差统计量（仅回喂、不生成动作量）：`μ_time`、`σ_time` 作为时间维度偏差的事实统计量回喂，**不产出「起飞时刻回填修正量」这一动作量**（起飞时刻调整属 B 组 14／D 组 7 的调度动作，跨组裁决 G-8）。
5. **产出校准建议（不写回）**：本功能只产出偏差样本、分层统计量与校准建议，**不直接修改 `sys_param`**。**纠偏阈值标定归 E 组**（其判据基于船侧预测偏差），**预测模型参数标定归 A 组**；`d_space` 含飞控跟随与末段交接误差（执行端），与 E 组判据量纲错配，故不得由本组标定纠偏阈值（跨组裁决 G-1）。

**关键判据**：

- 「持续偏大于」定义为滑动窗口内 `μ_space` 连续超过阈值比例达到 M 个采样周期（M 为参数），避免单次异常触发调整。
- 校准方向由偏差均值的符号与量级决定，校准幅度由标准差与分位数约束（不允许一次性调整超过当前值的一定比例，防止过冲）。

**用到的参数与阈值**（名目、分类与含义，取值见 `sys_param`）：

| 参数名                               | 分类  | 含义                    |
| --------------------------------- | --- | --------------------- |
| `rendezvous_dev_window_n`         | 窗口  | 滑动窗口样本数 N             |
| `rendezvous_dev_persist_m`        | 窗口  | 「持续偏大于」所需的连续采样周期数 M   |
| `rendezvous_dev_threshold_ratio`  | 阈值  | 触发纠偏阈值调整的偏差均值与当前阈值的比例 |
| `rendezvous_dev_max_adjust_ratio` | 阈值  | 单次校准允许的最大调整幅度比例（防过冲）  |

### 1.4 验证方式

| 验证项     | 数据 / 场景                                  | 指标             |
| ------- | ---------------------------------------- | -------------- |
| 偏差统计稳定性 | 仿真注入带系统性偏移的会面偏差，观察滑动窗口均值是否收敛到真实偏移量       | 收敛速度、稳态误差      |
| 校准方向正确性 | 分别注入「预测偏慢」「预测偏快」两种系统性偏差，校验纠偏阈值调整方向是否正确   | 方向正确率          |
| 抗抖动能力   | 注入随机噪声偏差（无系统性偏移），观察阈值是否保持稳定不被误调          | 误调次数（应为 0 或极少） |
| 分层有效性   | 同时注入不同机型 / 风况段的不同偏差，校验各层校准是否独立、不串扰       | 层间隔离度          |
| 闭环有效性   | 在带扰动注入的仿真中对比「开启回流校准」与「关闭回流校准」两组的会面偏差收敛曲线 | 偏差均值下降速率、稳态偏差  |

### 2.1 研究范围

| 序号    | 24                                             |
| 功能名   | 航线偏离检测                                         |

### 2.2 输入与输出

**输入**：

| 输入项     | 来源                                                         | 表示方式                                      | 粒度       |
| ------- | ---------------------------------------------------------- | ----------------------------------------- | -------- |
| 无人机当前位置 | M1 遥测流 `UavTelemetry.lon / lat / altM`，经 M4 飞行语义级清洗（M4-03） | 经纬度 ＋ 高度（已归一到基准坐标系，单位：度、米）                | 逐遥测点     |
| 规划可飞航迹  | M2 任务方案下发的无人机航迹（见 22 §5 第 5 步任务下达）                         | 有序航点列 `[(lon, lat, alt), ...]`，相邻航点间为直线航段 | 整条航迹，逐任务 |
| 当前飞行进度  | M4-09 飞行进度定位的输出（当前航段序号）                                    | 航段索引                                      | 逐遥测点     |

**输出**（见 22 §2「偏差与告警」、22 §5 第 6 步）：

| 输出项           | 去向                                   | 表示方式                                    |
| ------------- | ------------------------------------ | --------------------------------------- |
| 偏航距离          | M2（决策）、M5（展示）                        | 米，标量                                    |
| 告警级别（预警 / 严重） | M2（决策）、M5（展示），写入 `alert` 表（37 §5.12） | 功能分级：预警、严重；写入 `alert` 表时映射为级别字段的「警告、严重」 |
| 告警持续时长        | M2（决策）、M5（展示），写入 `alert` 表           | 秒，标量；供 E 组功能 9 映射四档（跨组裁决 G-6）           |
| 告警类型          | `alert` 表 `alert_type`               | `偏航`                                    |

**边界（明确不做什么）**：

- 不判断偏航后该怎么处置（继续、改航、返航），处置决策归 M2（见 20 §5、21 §7 兜底）。
- 不重新生成航迹，航迹生成归 M3；不直接向 M3 索取航线，航迹从 M2 下发的任务方案中获取（见 22 §5 第 5 步任务下达、34 §2）。
- 不做航迹级空域冲突检测（那是 M3 在第 5 步的二查，见 21 §5）。
- **高度字段（`altM`）虽随遥测传入，但不参与偏航判级**（G-10 已定）。接口契约须声明高度字段传递但不用于偏航分级计算。

### 2.3 算法设计

**选了什么做法、为什么选**：

采用「点到折线最短垂直距离 ＋ 双阈值分级」的做法。理由：

1. 可飞航迹是有序航点列，相邻航点间为直线航段，无人机当前位置到航迹的最短距离即点到折线的最短垂直距离。该方法几何意义明确、计算量小（O(n)，n 为航段数），适合秒级遥测频率下的实时计算。
2. 分级用双阈值而非单阈值：单阈值只有「偏 / 不偏」两态，无法区分「需要关注但不紧急」与「必须立即处置」。双阈值（预警阈值 < 严重阈值）给出两级，写入 `alert` 表时映射到级别字段（预警→警告、严重→严重，见 37 §5.12），也便于 M2 按级别采取不同处置。

**核心思路与步骤**：

1. **飞行进度定位**（M4-09）：沿航迹逐段比较，找到无人机当前位置投影落在哪一段（即点到该段的垂足落在线段内，或到该段端点距离最近），得到当前航段索引 `i`。这一步同时服务于 M4-05 进度与 ETA 计算。
2. **偏航距离计算**（M4-08）：计算当前位置到当前航段 `i`（若垂足落在线段外则到相邻航段）的最短垂直距离 `d_offtrack`。用 Haversine 或投影到局部平面后的欧氏距离（短距离下两者差异可忽略，取实现简单者）。
3. **分级判定**：
   - 若 `d_offtrack ≥ 严重阈值` → 告警级别 = 严重；
   - 若 `预警阈值 ≤ d_offtrack < 严重阈值` → 告警级别 = 预警；
   - 若 `d_offtrack < 预警阈值` → 不告警。
4. **告警去抖**：单次越阈不立即告警，需连续 `offtrackDebounceCount` 个遥测点越阈才触发，避免 GPS 抖动导致告警闪烁。告警解除需连续 `offtrackClearCount` 个点回到阈值内才清除（触发与解除用不同参数）。
5. **告警推送与记录**：触发告警时，通过 MQ 推 M2、WebSocket 推 M5，并写入 `alert` 表（`alert_type=偏航`，级别映射为 `alert` 表的「警告 / 严重」，即预警→警告、严重→严重）。
6. **告警等级随持续时长的更新规则**（跨组裁决 C-02）：
   - **升级条件**：偏航距离 ≥ 严重阈值 → 立即升级为严重（不做迟滞，偏航持续恶化不升级会延误处置）。预警 → 严重走快路径。
   - **等级上限**：严重，不再设更高等级。
   - **回落规则**：严重 → 预警——偏航距离持续回落至预警~严重区间，需连续 `offtrackDowngradeCount` 个遥测点满足才降级（降级做迟滞，避免 GPS 抖动导致级别反复）。预警 → 无告警——连续 `offtrackClearCount` 个点回到预警阈值内才清除。
   - **持续时长上报**：告警持续期间，持续时长字段随每条遥测更新，供 E 组功能 9 映射四档。

**关键判据**：

- 偏航距离是「到当前航段的最短垂直距离」，不是到最近航点的距离（后者在转弯处会误报）。
- 分级严格按阈值，不引入模糊区间；预警与严重互斥。
- 告警去抖窗口 K 必须 ≥ 1，K=0 等同于不去抖。

**用到的参数与阈值**（名目、分类与含义，取值见 `sys_param`）：

| 参数名                           | 分类  | 含义                            |
| ----------------------------- | --- | ----------------------------- |
| `offtrackWarningThreshold`  | 阈值  | 偏航预警阈值（米），超过即触发预警级告警          |
| `offtrackCriticalThreshold` | 阈值  | 偏航严重阈值（米），超过即触发严重级告警；须 > 预警阈值 |
| `offtrackDebounceCount`     | 窗口  | 告警去抖所需连续越阈点数 K                |
| `offtrackClearCount`        | 窗口  | 告警解除所需连续回到阈值内的点数              |
| `offtrackDowngradeCount`    | 窗口  | 严重→预警降级所需连续回到预警~严重区间的点数（C-02） |

> 说明：距离计算方式（Haversine 球面距离 vs 局部平面投影欧氏距离）为**实现时二选一的算法选择**，不作为可配置参数放入 `sys_param`（37 §5.14 分类无「开关」类）。短航程场景默认用 Haversine，精度足够；若航程极短或性能优先，可改用局部平面投影。

### 2.4 验证方式

| 验证项     | 数据 / 场景                             | 指标          |
| ------- | ----------------------------------- | ----------- |
| 偏航距离准确性 | 仿真中无人机沿航迹飞行，人为注入横向偏移，校验计算距离与真实偏移的误差 | 距离计算误差（米）   |
| 分级正确性   | 注入低于预警、介于两级、高于严重三种偏移，校验告警级别         | 级别判定正确率     |
| 去抖有效性   | 注入间歇性越阈（GPS 抖动模拟），校验告警是否被误触发        | 误触发次数       |
| 转弯段不误报  | 无人机在转弯航段正常飞行，校验是否被误判为偏航             | 转弯段误报率      |
| 实时性     | 遥测频率下逐点计算，校验单次计算耗时                  | 单帧耗时 < 遥测间隔 |

### 2.5 待定项

| #   | 事项                                     | 风险                                                                                                          |
| --- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 1   | 预警阈值与严重阈值的取值：长江航道宽度、桥梁净空、禁飞区距离都会影响合理取值 | 需结合航道实际宽度与安全余量确定，当前只能给仿真建议值                                                                                 |
| 2   | 高度维度是否纳入偏航判定：当前只算水平偏航，高度偏差是否单独检测       | **本组决定（跨组待定 G-10）**：首版只做水平偏航，不纳入高度维度。理由：需求 M4-11 只提偏航距离（水平），航道场景下高度由航路规划约束；如后续扩展须同步 F 组 21 的产量口径（F 产量、G 判级） |

| 序号    | 25                                     |
| 功能名   | 低电量预警                                  |

### 3.2 输入与输出

**输入**：

| 输入项        | 来源                                         | 表示方式                | 粒度        |
| ---------- | ------------------------------------------ | ------------------- | --------- |
| 无人机当前电量    | M1 遥测流 `UavTelemetry.battery`，经 M4 飞行语义级清洗 | 百分比（0–100）          | 逐遥测点      |
| 无人机 / 订单标识 | 遥测与任务方案                                    | `droneId`、`orderId` | 单值，每次任务一个 |

**输出**：

| 输出项   | 去向                                              | 表示方式                                                                                                                                    |
| ----- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 低电量告警 | **M2／E 组功能 10（能否回得了的能量判定）**、M5（展示），写入 `alert` 表 | `alert_type=低电量`，级别取警告或严重；**同一条告警的级别可随电量变化更新**（警告→严重即时、严重→警告经去抖，本组决定 G-4）。**量判分离（跨组裁决 G-7）**：本功能只做「电量低于阈值」的事实检测并告警；「能否回得了」由 E 组功能 10 判定 |
| 当前电量值 | M2（供返航复核时的事实输入）、M5                              | 百分比                                                                                                                                     |

**边界（明确不做什么）**：

- **不判断「还能不能飞完」**。能否完成归巢由 M2 在返航复核时按实际剩余电量 ＋ 实时风况判定（见 21 §8、22 §5 第 8 步）。M4 只上报「电量低于阈值」这一事实。
- 不决定返航 / 迫停 / 迫降的处置，处置归 M2。
- 不预测剩余电量（剩余航程估算归 M4-10，但那是距离估算，不是电量预测；电量预测归 M2 返航复核）。
- **首版阈值统一、不按机型区分**（G-11 已定）。`sys_param` 中参数键不带机型维度；接口契约须声明首版无机型维度，后续可扩展，无需改算法。
- **阈值来源与更新时机**（C-10 已定）：阈值数值由 M2 能耗模型倒推确定，部署时写入 `sys_param`；运行期间不动态更新（首版静态阈值）。若后续因实际能耗数据回流需要调整，由 M2 发起更新经 `sys_param` 写入（遵循 G-5：自动生成建议 ＋ M2 确认后写入），G 组不自行更新阈值。C 组 `soc_margin` 与 E 组 `e10_low_battery_abs` 均引用本组 G-11 同一阈值，三处读同一值。
- **`alert` 表级别字段可更新**（G-4 升级不迟滞、降级做迟滞）。低电量告警级别在持续期间会随电量变化（警告→严重即时、严重→警告经去抖），接口契约须声明 `alert` 表同一条告警的级别字段允许更新，不是只能写一次。

### 3.3 算法设计

**选了什么做法、为什么选**：

采用「单阈值事实检测 ＋ 迟滞比较」的做法。理由：

1. 需求明确本模块只做事实检测（M4-12「检测剩余电量低于阈值并上报」），不引入预测模型，保持职责单一。
2. 单阈值检测若直接用 `battery < threshold` 触发 / 清除，电量在阈值附近抖动时会导致告警反复触发。迟滞比较（触发阈值与清除阈值不同）可消除抖动。
3. 告警级别与电量低于阈值的程度挂钩：轻度低于阈值为警告，严重低于为严重，便于 M2 与 M5 区分紧急程度。

**核心思路与步骤**：

1. **读取电量**：从清洗后的遥测取 `battery` 字段（百分比）。
2. **迟滞比较**：
   - 当前无低电量告警时，若 `battery < lowBatteryTrigger` → 触发低电量告警。
   - 当前有低电量告警时，若 `battery > lowBatteryClear` → 清除告警。
   - `lowBatteryClear > lowBatteryTrigger`（迟滞带，避免抖动）。
3. **分级**（升级不做迟滞、降级做迟滞）：
   - 当前为警告时，若 `battery < lowBatterySevere` → **立即升级为严重**（不做迟滞。低电量单调下降，升级迟滞会延误返航，本组决定 G-4）。
   - 当前为严重时，若 `battery ≥ lowBatterySevere` → 需连续 `lowBatteryDowngradeDebounce` 个遥测点满足，才**降级为警告**（降级迟滞，避免电量抖动导致级别反复）。
   - 即：警告 → 严重走快路径（即时）；严重 → 警告走慢路径（去抖）。
4. **上报**：通过 MQ 推 M2、WebSocket 推 M5，写入 `alert` 表（`alert_type=低电量`）。

**关键判据**：

- 迟滞带必须存在（`clear > trigger`），否则等价于无迟滞。
- 严重阈值必须 ≤ 触发阈值（`severe ≤ trigger`），否则分级逻辑矛盾。
- 电量字段来源唯一（M1 遥测经 M4 清洗后），M4 不另建电量来源。

**用到的参数与阈值**（名目、分类与含义，取值见 `sys_param`）：

| 参数名                              | 分类  | 含义                                   |
| -------------------------------- | --- | ------------------------------------ |
| `lowBatteryTrigger`            | 阈值  | 低电量告警触发阈值（百分比），低于此值触发告警              |
| `lowBatteryClear`              | 阈值  | 低电量告警清除阈值（百分比），高于此值清除告警；须 > trigger  |
| `lowBatterySevere`             | 阈值  | 低电量严重阈值（百分比），低于此值告警级别为严重；须 ≤ trigger |
| `lowBatteryDowngradeDebounce` | 窗口  | 严重→警告降级所需连续满足点数（升级不做迟滞、降级做迟滞）        |

### 3.4 验证方式

| 验证项      | 数据 / 场景                | 指标               |
| -------- | ---------------------- | ---------------- |
| 触发与清除正确性 | 仿真中电量从高到低再回升，校验触发与清除时刻 | 触发 / 清除时刻偏差      |
| 迟滞防抖     | 电量在阈值附近注入抖动，校验告警是否反复   | 反复触发次数（应为 0 或极少） |
| 分级正确性    | 注入不同电量值，校验警告 / 严重级别    | 级别判定正确率          |
| 边界值      | 电量恰好等于各阈值时的判定          | 边界判定一致性          |
| 不越界      | 确认 M4 只上报、不做返航决策       | 检查 M4 输出不含处置指令   |

### 3.5 待定项

| #   | 事项                                                    | 风险                                                                                        |
| --- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 1   | 三级阈值（trigger / clear / severe）的取值：依赖机型续航、返航能耗、安全余量    | 需结合 M2 返航复核的能耗模型倒推，当前只能给仿真建议值                                                             |
| 2   | 是否需要按机型区分阈值：不同机型续航差异大，统一阈值可能对续航长的机型过严                 | **本组决定（跨组待定 G-11）**：首版统一阈值（不按机型区分），降低落地复杂度。`sys_param` 中预留机型维度的扩展能力，后续若机型差异显著可按机型配置，无需改算法 |
| 3   | 告警级别是否需要「提示」一级（`alert` 表级别含提示 / 警告 / 严重）：当前低电量只用警告与严重 | **本组决定**：G 组五项告警均不产生「提示」级，仅用「警告 / 严重」两档；待与 M5 展示侧对齐语义（不影响接口契约，仅影响 M5 展示）                  |

### 4.1 研究范围

| 序号    | 26                                  |
| 功能名   | 失联检测                                |
| 所属模块  | M4                                  |
| 需求条目  | M4-13（落点 34 §3.4），配合 NF-6「失联不等于灭失」  |

### 4.2 输入与输出

**输入**：

| 输入项        | 来源                               | 表示方式                 | 粒度        |
| ---------- | -------------------------------- | -------------------- | --------- |
| 遥测心跳       | M1 遥测流 `UavTelemetry`，每条遥测点即一次心跳 | 含 `uavId`、`ts`（打点时间） | 逐遥测点      |
| 无人机 / 订单标识 | 遥测与任务方案                          | `droneId`、`orderId`  | 单值，每次任务一个 |
| 最后已知位置     | M4 维护的最近一次有效遥测位置                 | 经纬度 ＋ 时间戳            | 单值，随遥测更新  |

**输出**：

| 输出项                | 去向                                                 | 表示方式                         |
| ------------------ | -------------------------------------------------- | ---------------------------- |
| 失联状态               | M6 无人机表 `drone.status`（23 §7），M5 展示                | 状态 = 失联                      |
| 失联告警               | M2（决策：按最后已知指令执行 ＋ 自主返航，见 21 §7 兜底）、M5，写入 `alert` 表 | `alert_type=失联`，级别 = 严重      |
| 灭失推定上报（M4 输出）      | M2，写入 `alert` 表                                    | 方案 B（2026-10-16 裁决）：不新建告警类型、级别不升级，仍为 `alert_type=失联`／严重，以 `LOSS_DECLARED` 相位补发一次同一事件（复用原 eventId），M2 据此触发货物灭失、订单异常终止 |
| 货物灭失、订单异常终止（M2 决策） | M2 决策后写 M6：货物转 `灭失`（23 §6）、订单转 `异常终止`（23 §3）       | M4 不自行改货物 / 订单状态             |

**边界（明确不做什么）**：

- 不直接将无人机置为灭失。灭失推定需「失联持续超过灭失判定窗口」，且最终货物灭失、订单异常终止的决策归 M2（见 23 §8 写入方）。
- 不做搜寻与救援决策（21 §7 兜底「按最后已知位置与时间外推搜寻」归 M2 / 人工）。
- 不检测链路层断连（那是 M1 连接生命周期管理 M1-06 / M1-18 的职责）。M4 检测的是「该收到的遥测没收到」这一应用层事实。
- **心跳唯一来源为 M1 `UavTelemetry.ts`**（G-13 已定）。接口契约须声明心跳字段以遥测打点时间为准，不引入第二个心跳源；链路层状态后续若可消费，仅作为可选增强，不改变主判定逻辑。
- **灭失推定仅由 M4 上报事件，状态变更由 M2 写 M6**（G-12 已定）。接口契约须声明 M4 输出「灭失推定事件」，货物转 `灭失`、订单转 `异常终止` 由 M2 执行；人工撤销动作亦由 M2 侧发起，M4 不写货物 / 订单状态。

### 4.3 算法设计

**选了什么做法、为什么选**：

采用「心跳超时两级判定 ＋ 状态机驱动」的做法。理由：

1. 失联的本质是「在预期时间窗口内未收到该无人机的遥测」，用心跳超时检测是最直接的判据。无人机状态机已定义「失联」状态（23 §7），检测结果直接驱动状态流转。
2. 失联 ≠ 灭失是项目明确的安全原则（NF-6、21 §7 兜底、23 §7）。若心跳一断就推定灭失，会导致货物被误判灭失、订单被误终止，而实际可能只是通信短暂中断。因此必须设两个窗口：失联窗口（断连即触发失联）与灭失窗口（失联持续超时才推定灭失）。
3. 两级判定给 M2 留出处置时间：失联后 M2 可触发「按最后已知指令执行 ＋ 自主返航」（21 §7），若在灭失窗口内恢复通信则不推定灭失。

**核心思路与步骤**：

1. **心跳时间维护**：每收到一条该无人机的有效遥测，更新 `last_heartbeat_ts[uavId] = ts`。
2. **失联判定**：以当前时刻 `now` 与 `last_heartbeat_ts` 比较，若 `now − last_heartbeat_ts > 失联判定窗口` 且无人机当前状态为「执行任务中」或「返航中」，则判定失联：
   - 写入 `drone.status = 失联`；
   - 推送失联告警（`alert_type=失联`，级别 = 严重）至 M2、M5，写 `alert` 表。
3. **灭失推定**（方案 B，2026-10-16 裁决）：若无人机处于「失联」状态且 `now − last_heartbeat_ts > 灭失判定窗口`，则推定灭失：
   - **不新建告警类型、级别不升级**：灭失与失联同为 `alert_type=失联`／严重；
   - M4 以 `LOSS_DECLARED` 相位**强制补发一次事件**，复用失联首发的 eventId 与首发时刻（供 M2 识别灭失时点），由 M2 决策货物转 `灭失`、订单转 `异常终止`（见 23 §8）；
   - M4 不自行改货物 / 订单状态。
4. **恢复处理**：若失联后、**灭失前**重新收到遥测，则清除失联状态，`drone.status` 回到失联前状态（执行任务中或返航中），清除失联告警（活跃告警表 resolve，再失联以新 eventId 起事件）。**灭失推定后迟到的遥测不自动复活**（G-12：自动推定＋人工可撤销，撤销由 M2 侧执行）。

**关键判据**：

- 失联判定窗口 < 灭失判定窗口（两级递进）。
- 失联判定只对「执行任务中」「返航中」的无人机生效；地面空闲 / 维护中的无人机不检测失联（其遥测可能本就低频或关闭）。
- 心跳来源唯一（M1 遥测流），M4 不另发探测包。
- 时间比较统一用绝对时间戳，`last_heartbeat_ts` 取遥测打点时间 `ts`（非 M4 接收时间），避免网络延迟引入偏差。

**用到的参数与阈值**（名目、分类与含义，取值见 `sys_param`）：

| 参数名                        | 分类  | 含义                                 |
| -------------------------- | --- | ---------------------------------- |
| `heartbeatLostWindowSec`    | 窗口  | 失联判定窗口（秒），超过此时长未收到遥测判失联            |
| `heartbeatLossWindowSec`    | 窗口  | 灭失判定窗口（秒），失联持续超过此时长推定灭失；须 > 失联判定窗口 |

### 4.4 验证方式

### 扩.3 算法设计

**选了什么做法、为什么选**：

采用「双阈值绝对值检测 ＋ 变化率突变检测 ＋ 迟滞防抖」的做法。理由：

1. 风速超限有两种形态：**绝对值超限**（持续大风）与**突变**（阵风，短时间内风速急升）。绝对值超限用双阈值分级；突变用变化率检测，即使绝对值未到严重阈值，突变本身也可能导致姿态失控，需单独告警。
2. 双阈值分级（预警 < 严重）与功能 24、25 保持同构，便于 E 组功能 9 统一映射四档处置。
3. 风速传感器易受无人机旋翼下洗、姿态变化影响，需迟滞防抖避免告警闪烁。

**核心思路与步骤**：

1. **读取风速**：从清洗后的气象数据取当前风速 `v_wind`（m/s）。
2. **绝对值分级判定**：
   - 若 `v_wind ≥ weatherWindCriticalThreshold` → 告警级别 = 严重；
   - 若 `weatherWindWarningThreshold ≤ v_wind < weatherWindCriticalThreshold` → 告警级别 = 警告；
   - 若 `v_wind < weatherWindWarningThreshold` → 不触发绝对值告警。
3. **突变检测**：计算最近 `weatherSurgeWindowSec` 秒内的风速变化率 `Δv/Δt`：
   - 若 `Δv/Δt ≥ weatherWindSurgeThreshold` → 触发突变告警（级别至少为警告，若同时满足绝对值严重则取严重）。
   - 突变检测不依赖绝对值是否超限，阵风本身即危险。
4. **迟滞防抖**：告警触发后，需风速连续 `weatherClearDebounce` 个采样点低于预警阈值（且无突变）才清除告警，避免阵风间隙误清除。
5. **上报**：通过 MQ 推 M2、WebSocket 推 M5，写入 `alert` 表（`alert_type=气象超限`）。
6. **告警等级随持续时长的更新规则**（跨组裁决 C-02）：
   - **升级条件**：风速 ≥ 严重阈值 或 突变触发 → 立即升级为严重（不做迟滞）。预警 → 严重走快路径；若同时满足绝对值严重与突变，取严重。
   - **等级上限**：严重，不再设更高等级。
   - **回落规则**：严重 → 预警——风速持续 < 严重阈值且无突变，需连续 `weatherClearDebounce` 个采样点满足才降级（降级做迟滞，避免阵风间隙导致级别反复）。预警 → 无告警——连续 `weatherClearDebounce` 个点 < 预警阈值且无突变才清除。
   - **持续时长上报**：告警持续期间，持续时长字段随每个采样点更新，供 E 组功能 9 映射四档。

**关键判据**：

- 严重阈值必须 > 预警阈值。
- 突变检测窗口内至少需要 2 个采样点才能计算变化率。
- 风速来源唯一：订阅 M1 发的 `data.weather`（地面气象站/机载传感器融合由 M1 内部定），单值消费，M4 不另建风速来源。

**用到的参数与阈值**（名目、分类与含义，取值见 `sys_param`）：

| 参数名                               | 分类  | 含义                              |
| --------------------------------- | --- | ------------------------------- |
| `weatherWindWarningThreshold`  | 阈值  | 风速预警阈值（m/s），超过即触发警告级告警          |
| `weatherWindCriticalThreshold` | 阈值  | 风速严重阈值（m/s），超过即触发严重级告警；须 > 预警阈值 |
| `weatherWindSurgeThreshold`    | 阈值  | 风速突变阈值（m/s 每秒），变化率超过即触发突变告警     |
| `weatherSurgeWindowSec`            | 窗口  | 突变检测的时间窗口（秒），计算该窗口内的风速变化率       |
| `weatherClearDebounce`          | 窗口  | 告警清除所需连续低于预警阈值的采样点数             |

### 6.3 边界（不产出什么）

- **不写 `sys_param`**：只产偏差样本、统计量与校准建议（G-1）
- **不判断处置**：继续/改航/返航/终止归 E 组功能 9（G-6）
- **不做能量可行性判定**：能否回得了归 E 组功能 10（G-7）
- **不产起飞时刻回填修正量**：动作量属 B 组 14/D 组 7（G-8）
- **不产量**：距离/投影点/航段量归 F 组（G-9）
