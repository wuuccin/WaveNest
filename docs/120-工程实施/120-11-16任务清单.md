## 2 顺序

本批按四层推进，每一层都有自己的前提与合并门槛。

| 层 | 前提 | 可开工的人 | 合并门槛 |
|---|---|---|---|
| 1 | 无 | 吴可欣、杨添爻、彭紫情 | 七项裁定与一项契约回填书面定死；`22` 的十一字段与 `OrderView`、`DispatchGate` 逐字一致；`53-开放问题` 登记到位 |
| 2 | 2-1 以 1-2 与 1-3 的裁定为前提；2-2 与 2-4 以 1-6 的裁定为前提；2-3 以 1-4 的裁定为前提 | 张睿哲、吴可欣 | 每段可以独立测试；算法侧的断言与模块侧的断言分开归属；改表 SQL 有组长的点批；既有测试不回归 |
| 3 | 3-1 以 2-2 与 2-4 的合入为前提；3-2 以 1-1 与 1-7 的裁定为前提；3-3 以 1-8 的裁定为前提；3-4 以 1-8 的实测数为前提；3-5 以 3-4 为前提 | 卢肄文、吴可欣、彭紫情、杨添爻 | 全量构建零失败；第三级可以生成航迹并下发指令；复核三值在现场可以查到；回放不再出现状态未变的复核步骤；偏航与低电量可以现场造出 |
| 4 | 序号一至序号三全部合入 `develop` | 吴可欣、罗才辉、彭紫情 | 4-1 与 4-2 当日完成；4-3 的两段录屏与剧本逐段对齐；`git diff --check` 零输出；文件清单与点批的范围一致 |

序号一内部按「迫降点的退化口径、契约字段、复核出口、回落参数、其余裁定」的先后推进。序号二按独占路径并行。序号三按「闸门解除侧的验证、订单唤醒侧的验证、其余各项并行」的先后推进。序号四按「全量构建、独立复核、重录」的先后推进。灌库、起服务、跑测试与录屏属于作者的自验，不占序号。

这样的顺序安排有一个明确的理由：序号一的裁定是后续各层的输入，裁定没有定死之前，实现的改动会反复返工；序号二的读键与字段是序号三的模块接入的前提，落点选择器没有输出标识之前，模块层无法生成航迹；序号四的构建必须等前三层的全部合入，否则构建的结果不能代表全批的终态。把作者的自验排除在序号之外，是为了让序号的推进只反映跨人的依赖，不把个人的环境准备算成团队的进度。

## 4 与 11-14 批次的关系

本批与 11-14 批次不是同一批任务。11-14 批次的 3-1 是罗才辉对 11-14 合入结果的交叉复核，已经在 2026-11-16 完成，记录在 [2026-11-16-罗才辉-第三层汇合复跑交叉复核](../50-过程记录/2026-11-16-罗才辉-第三层汇合复跑交叉复核.md)。本批的 4-2 是罗才辉对 11-16 全批的独立验收，两者复核的对象不同，不能互相替代。把两批复核混为一谈的写法会让读者误以为 4-2 已经完成，实际的 4-2 仍然没有开始。

本批的 4-1 已经在 2026-11-18 完成，全量构建为 `BUILD SUCCESSFUL`，一千二百四十二条测试零失败、零错误、两条跳过。两条跳过都是既有的 `@Disabled` 用例，与本批的改动无关。4-1 的结论登记在 [51-变更记录](../50-过程记录/51-变更记录.md) 的第 31.33 节。4-1 的三项复核分别是 `git diff --check` 的零输出、`git status --porcelain` 的零输出与 `git show --name-only` 的两文件清单，这三项都写在 `51` 的收口登记里，读者可以按节名直接定位。

本文件的状态回写遵循一条固定的口径：以 `develop` 的合并提交为唯一的依据，不以个人的分支、个人的本地构建或个人在工作群的通报为依据。这样处理的原因是个人分支的提交在合并之后可能被压缩、改写或丢弃，工作群的通报也可能在发出之后被后续的提交推翻，只有合并提交的树是仓库的最终事实。对于读者关心的「某项是否真的可用」，本文件只回答「是否已经合入」，可用的验证与遗留的边界放在对应的过程记录里，避免把「已经合入」与「已经验收」混成同一个结论。这样的分工让任务清单保持简洁，也让过程记录承担证据的职责，两者的边界清晰，读者不会因为一处过期的状态而误判全批的进度。
