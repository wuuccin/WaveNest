## 一、三问逐项回答

### 1. `alert.event` 现在有没有消费方？

**没有。** 全仓（含 develop）不存在任何 `@RabbitListener` 订阅 `alert.event`（`TopicName.ALERT_EVENT`）。当前链路状态：

```
检测器 → AlertRecorder → ① 写 alert 表 + ② 发 alert.event MQ
                                                    ↓
                                          发出后无人订阅（暂存于 MQ，无积压风险——
                                          topic 交换机无绑定队列时消息直接丢弃，不报错）
```

- 消费方规划中：前端 push 出口（彭紫情侧）接 `alert.event` 驱动大屏红闪；
- **影响**：不影响 M4 侧任何功能，发送成功即履约；联调红闪要等消费端接入。

### 2. `alert` 表有没有写入？

**代码侧：有，fail-soft 写八列。** `AlertRecorder.persist` 按实表八列写入：

```
alert_id / drone_id / order_id / alert_type / level / trigger_time / handle_status / handle_record
```

`duration`／`current_value`／`threshold_value` 三列**不落表**，只随 `alert.event` 消息携带（37 §5.12 口径）。写表异常仅记 warning、不阻断 MQ 发送（fail-soft 设计，避免检测链被 DB 抖动打断）。

**实际写入：待实测**——依赖 ④ 起服务后仿真遥测触发检测（偏航/低电量），届时查 `alert` 表行数与内容补录。当前仿真数据（风 5±1.5 m/s、电量正常）下预计无告警产生，属正常。

### 3. `CLEARED` 会不会发事件？

**不会。** `AlertRecorder.resolve`（告警恢复）只做两件事：更新内部活跃告警状态 ＋ 更新表记录（如需），**不发任何 MQ 事件**。

- 这是 `48` 决议 2 的**既定事实**，不是缺陷：M2 已明确不消费 `alert.event` 判恢复（因为无清除事件可判），M2 的恢复判定走自身数据通路（如风值防抖），不依赖 M4 的清除通知；
- 后果：`alert.event` 上只会出现 `触发` 与 `升级/补发` 两类消息，下游不应期待 `CLEARED` 帧。
