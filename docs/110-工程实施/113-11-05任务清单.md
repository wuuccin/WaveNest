## 8 注意点

1. 每笔合并请求的 base 是 `develop`；合并后由吴可欣跑 `git show --name-only` 复核无文档夹带。
2. 新增 SQL 只在空数据卷执行；已有卷要手工执行。两种执行方式都写进合并请求描述。重灌会清掉全部订单与日志。
3. 分段限速配置与气象网格都会改变预测与调度的数值。分段限速配置随第一批先合入；若晚于第二批实现合入，则预计送达落库、会面点与航迹起点按货巢、汇合复跑三处要按新数值重写断言。受影响的实验结论在合并请求描述写新数字并注明旧数字作废；已归档的阶段二报告数字不追改，只在最终核对与收口里注明口径变更。
4. 分段限速配置值约束：前两段限速不低于实测船速四点一二米每秒，末段低于四点一二米每秒，否则无法自证限速生效。
5. 评审条目按第 6 节的分派执行，不跨文件抢改；同一文件的评审项与主链改动合并成一次提交。
6. 新发现的未解决代码问题写进合并请求描述，并在本文末尾追加遗留行，不另建台账文件。
7. 实验产物不进仓库，脚本、截图、导出数据只把数字写进合并请求描述。
8. 模块二调用模块三时只调会面门面，模块二侧不出现航迹生成器静态调用。
9. 汇合复跑前先拉取 `develop`，四件套健康后才能跑含真实 MySQL 的集成测试。
10. 个人区文件行尾用 LF，仓库 `docs/**` 行尾用 CRLF，两者不混。
11. 构建只用 Wrapper，复跑命令为 `./gradlew build --no-build-cache --rerun-tasks`；不加这两个参数会命中构建缓存，测试不会真跑。
