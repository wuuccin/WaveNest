# 10 月 31 日告警位置回放 Redis 复验记录 宋冰鑫

## 一 任务

按 `108-回放缺帧修复计划` 的分工，彭紫情主改飞行轨迹存储的介质，从内存改为 Redis；宋冰鑫配合验证告警位置回放在 Redis 下仍正确，对应验收判据的第三条，即告警落库与位置回放不退化。验证必须在 Redis 版存储上做，不能与核心改动并行。

## 二 环境与代码基线

- 代码：基于 `origin/fix/18-front`，其中包含彭紫情的改动 `4ddf9b1`，提交说明为把回放帧持久化到 Redis；另建验证分支，未改核心实现。
- Redis：`wavenest-redis` 容器在跑，键为 `flight:track:{flightId}` 的 zset，成员为标识与遥测状态 JSON 的拼接。
- 后端：以应用模块启动，端口改为 18080，关闭仿真。本机 8080 被另一个无关服务占用，改端口不影响被测链路。
- 注入：用消息队列的 HTTP 接口发无人机遥测，与 10-30 复验同一手段。
- 环境原本没有 `flight:track` 前缀的键，本轮数据均为新写入。

## 三 被测链路

告警记录器取位置的链路未变，顺序为告警记录入口调用最后已知位置方法，转到飞行轨迹存储的回放方法，再从后往前找第一帧非补插且几何可用的记录。

Redis 版回放多了两层处理：zset 按时间戳排序，每帧遥测状态走 JSON 往返。风险点有三项，分别是补插标记能否原样回来、状态缺失与 NaN 坐标能否安全存取、重启后新实例能否读到旧帧。本记录逐条给证据。

## 五 真实环境验证

### 5.1 告警位置在 Redis 下取最后已知实测帧

注入测试机四帧，速度按每秒十二米、每帧间隔一点二秒，前三帧电量一百，第四帧电量十五。

| 帧 | 经度 | 纬度 | 电量 |
|---|---|---|---|
| 1 | 115.88000 | 28.68000 | 100 |
| 2 | 115.88013 | 28.68019 | 100 |
| 3 | 115.88026 | 28.68038 | 100 |
| 4 | 115.88039 | 28.68057 | 15 |

告警表结果为低电量、警告级、测试机、经纬度取第四帧、当前值 15、阈值 20。`flight:track` 中四帧全在，告警位置等于第四帧，当前值与阈值落库正常，告警位置四列扩项未退化。

### 5.2 位置跳变帧经 Redis 后仍正确回退

另一台测试机先按每帧五百米注入，超过速度阈值，清洗层把第二帧到第四帧判为位置跳变，状态为缺失、坐标为 NaN，但仍然写入 Redis，zset 基数为 4。告警行的经纬度为第一帧的 `115.88000 / 28.68000`。

告警位置回退到第一帧实测位置，说明最后已知位置判据在 Redis 下仍成立；NaN 坐标帧存盘与回放均未抛错，Redis 内该帧 JSON 写作字符串形式的 NaN。

### 5.3 后端重启后回放补齐帧不丢

停掉后端进程再起，Redis 不动。查询第一台测试机的回放仍返回重启前四帧，时间戳为 `1793443581853`、`1793443584360`、`1793443585647`、`1793443586905`，坐标与上表一致，第四帧电量为 15。第二台测试机的回放返回四帧。回放统计返回两架次、八个样本、零个补插样本。

### 5.4 重启后告警仍能取位置并落库

重启后注入第三台测试机单帧，坐标为 `115.9000 / 28.7000`，电量为 15。告警行为低电量、警告级、经纬度 `115.9 / 28.7`、当前值 15、阈值 20、触发时间 2026-10-31 18:48:35。

重启后告警记录器与 Redis 存储的接线正常，位置与检测值照常落库，该机在 `flight:track` 中有一帧。

## 六 结论

- 通过。Redis 版存储下，告警位置回放口径与内存版一致：取最后已知真实上报帧，跳过补插帧与无位置帧，无实测帧时留空。
- JSON 往返未破坏判据所需字段，补插标记、状态缺失与 NaN 坐标都能原样存取；重启后新实例可读到重启前帧；四个方法签名与下游零改动。
- 告警落库未退化：三架测试机三行告警的经纬度、当前值与阈值均正确。
- 单元测试与真实 Redis 两条证据齐备，全模块十七个测试类回归通过。

## 七 观察项与归属

| 事项 | 归属 | 说明 |
