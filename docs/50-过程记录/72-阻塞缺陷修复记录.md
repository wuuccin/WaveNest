## 1 缺陷一：组装层启动直接失败

### 1.1 症状

```
.\gradlew.bat :wl-app:bootRun
...
UnsatisfiedDependencyException: Error creating bean with name 'rescheduleService':
  Parameter 3 of constructor ... required a bean of type
  'com.waterlogistics.dispatch.homecoming.HomecomingService' that could not be found.

APPLICATION FAILED TO START
```

### 1.2 根因

`RescheduleService` 合并 6b 桥段与重派逻辑后，构造参数新增了 `HomecomingService`。
而 `HomecomingService` 是**裸 POJO，没有 `@Service`**：

```java
public class HomecomingService {   // ← 扫不到
```

`wl-app` 的 `WaveNestApplication` 靠组件扫描取业务 Bean：

```java
@SpringBootApplication(scanBasePackages = "com.waterlogistics")
```

扫描只认 `@Service` / `@Component` / `@Configuration`。`wl-m2-dispatch` 内其余 14 个类
都带注解，**唯独此类漏标**，于是启动期找不到 Bean。

**本质是合并时的漏配**，不是设计问题：算法能力（`algo.inflight` 三级判定）是对的，
只是模块层编排类没声明自己是 Bean。

### 1.3 修法

给 `HomecomingService` 加 `@Service`，与本模块其余类一致。
本类无任何注入依赖（只有静态 `log`），默认无参构造，**不影响单测里直接 `new` 的用法**。

## 2 缺陷二：MQ 全链路消息 100% 发不出去

### 2.1 症状

启动后日志每秒刷屏，且**不影响进程存活**：

```
WARN  c.w.collector.publisher.MqDataPublisher : publish failed: routingKey=data.ais,
  err=SimpleMessageConverter only supports String, byte[] and Serializable payloads,
  received: com.waterlogistics.contract.mq.AisMessage
WARN  ... routingKey=data.uav.telemetry ... received: ...UavTelemetry
WARN  ... routingKey=data.weather       ... received: ...WeatherData
```

### 2.2 根因（三层叠加，逐层放大）

**第一层 —— 装配层没引 AMQP 依赖。** `wl-app/build.gradle.kts` 原先只有
`spring-boot-starter-websocket`，没有 `spring-boot-starter-amqp`。
运行时虽因传递依赖拿到了 `RabbitTemplate`，但**没有人在编译期提供 JSON 消息转换器**，
`RabbitTemplate` 与 listener container 都落到容器默认的 `SimpleMessageConverter`——
它只支持 `String` / `byte[]` / `Serializable` 三种载荷。

**第二层 —— 契约载荷全是 record，不实现 `Serializable`。**
《22》约定的 `AisMessage` / `UavTelemetry` / `WeatherData` 等均为 record，
record 默认不实现 `Serializable`，于是 `convertAndSend` **每一条都被拒**。

**第三层 —— 失败被降级为 warn，作业照跑。**
`MqDataPublisher#send` 的异常处理是「发布失败不阻断采集节拍（下一节拍继续）」，
只 `log.warn`。**这是当时的设计意图（采集不该被 MQ 拖停）**，但与前两层叠加后
变成最坏形态：**日志在刷警告，作业照跑，但 M1 一条数据都进不了 MQ**，
M2 的预测刷新驱动链（`AisIngestListener`）与 M4 的监控链全部静默失效——
**没有报错、没有异常，只是什么都没发生**。

这两层的坑早被写在注释里，只是补丁一直没人做：

| 位置 | 原文 |
|---|---|
| `AisIngestListener`（M2） | 「按 `AisMessage` 接收，要求容器配置 JSON 消息转换器……应在统一配置里补 `MessageConverter`，**不在本类里解析字符串**」 |
| `PredictionConfig` 等 | 同口径要求转换器配置归一 |

### 2.3 修法

**在装配层新增 `wl-app/.../app/config/MqMessageConverterConfiguration`，
定义全项目唯一的 JSON 消息转换器 Bean：**

```java
@Bean
public MessageConverter mqJsonMessageConverter() {
    JsonMapper mapper = JsonMapper.builder()
            .disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
            .build();
    return new JacksonJsonMessageConverter(mapper);
}
```

Spring Boot 会自动把它应用到 `RabbitTemplate` 与
`SimpleRabbitListenerContainerFactory`，**各业务模块无须各自配置**，
收发两侧共用同一套口径，避免分叉。

**为什么是 `JacksonJsonMessageConverter` 而不是 `Jackson2JsonMessageConverter`？**
本项目是 Spring Boot 4.1.1 ＋ **Jackson 3**（包名 `tools.jackson`，
见 `backend/README.md` §四「Spring Boot 4.x 三处差异」）。
Jackson 3 对应的转换器是 `JacksonJsonMessageConverter`；
老名字那套基于 Jackson 2（`com.fasterxml`），**本项目 classpath 上根本没有**。
按老教程抄类名会直接编译失败。

### 2.4 两处取舍（有意为之，不是疏漏）

| 取舍 | 理由 |
|---|---|
| 关闭 `FAIL_ON_UNKNOWN_PROPERTIES` | 契约对象按《22》持续演进。消费侧先收到自己还不认识的新字段时，**不应整条消息反序列化失败**——否则上游加一个字段就会打停下游全链路 |
| **不开**类型推断（不设 inferred type id header） | 消费侧靠 `@RabbitListener` 方法签名确定目标类型即可。开启 `__TypeId__` 会引入受信任包（trusted packages）限制与反序列化安全面，本项目消息类型全部由代码固定，无需该机制 |

## 6 复盘要点（给后续开发的两条硬规矩）

**其一：注入依赖前先确认对方是不是 Bean。**
`wl-app` 只有组件扫描这一条取 Bean 的路（除 `@MapperScan`）。
模块层新增协作类时，要么自带 `@Service`，要么在装配层显式 `@Bean`——
**两头都不做就是本文 §1 那个启动失败**。

**其二：失败降级为 `warn` 时，必须同时有可观测的失败计数或告警。**
`MqDataPublisher` 的「不阻断采集节拍」是对的，
但配合「转换器没配」就变成了静默失效。
本次能发现，是因为人工去读了日志并追到了交换机。
**建议**：后续为 `send` 的失败加一个计数（Micrometer 或定时汇总），
让「消息发不出去」变成**可监控**指标，而不是靠人盯日志。

## 8 2026-10-30 追加缺陷：回放接口读内存

### 8.1 症状

T4 主故事三遍连跑的中间一遍执行了后端重启。实时推送恢复，订单续到完成，但回放只拿到 371 帧，且全部为重启之后的帧，重启之前 0 帧。同一时间库里 `flight_point` 有 4083 行，跨重启无缺口。

### 8.2 根因

回放接口读内存，不读库。调用链为 `FlightQueryController.replay()` 到 `FlightQueryService.replay()` 到 `FlightRecordStore`。`FlightRecordStore` 的结构为 `Map<String, List<TelemetryState>> records = new ConcurrentHashMap<>()`，位于 `wl-m4-monitor/.../store/FlightRecordStore.java`，纯内存且无落库。后端重启后 JVM 内存清空，回放只剩重启后的帧。落库与回放是两条独立链路，`flight_point` 的连续性不能补偿回放的内存依赖。

### 8.3 修法方向

两条路任选一条，落点都在 `wl-m4-monitor` 的 store 层：

1. 回放改为读 `flight_point`，按任务或机号分页取点。
2. 服务启动时从 `flight_point` 回填内存仓，回放仍读内存。

方案 1 的读取成本随历史增长，方案 2 的启动成本随历史增长。选择时须说明取舍，不得两条都不做。

### 8.4 可复现的验法

在飞行途中重启后端，重启前后各调一次 `GET /api/replay/{droneId}`，比对返回帧的时间范围是否覆盖重启点。覆盖即通过，只含重启后帧即不通过。

### 8.5 遗留项

该缺陷尚未修复，已登记 `52-待办清单` §1.3 第 21 项。功能口径见 `34-M4-飞行任务监控` §3.5 的实现备注。
