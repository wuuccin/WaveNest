## 2 环境修复

第一次全量构建在 `wl-app:test` 阶段失败，四条用例没有通过。失败的直接原因是 Redis 的连接被拒，日志里反复出现 `Unable to connect to 192.168.204.191:6380` 与 `Connection refused`。构建开始前 6380 是可达的，构建过程中变成不可达，说明 Redis 容器在构建中途退出了。

登入虚拟机后确认 `wavenest-redis` 处于 `Restarting` 状态。容器日志给出了根因：`Bad file format reading the append only file appendonly.aof.1.incr.aof`。Redis 的增量 AOF 文件损坏，进程每次启动都在加载阶段退出，容器因此不断重启。

修复的做法分三步。第一步停止容器。第二步用一个临时的 Redis 容器挂载同一个数据卷，把整个 `appendonlydir` 复制为 `appendonlydir.bak`，再删除原始的 `appendonlydir`，让 Redis 在下次启动时按空缓存重建。第三步启动容器并执行 `redis-cli ping`，返回 `PONG`，宿主机的 6380 也恢复可达。

这项修复只影响 Redis 的缓存内容，不影响 MySQL 里的历史数据。备份目录保留在数据卷内，需要回溯时可以取回。修复完成后重新执行同一条构建命令，`wl-app:test` 的四条用例全部通过。第一次的失败属于环境故障，不是本批代码的回归。

环境修复的判断依据也需要写清。第一次失败的日志里有明确的连接拒绝，四条失败用例的堆栈都指向同一个 Redis 地址，且该地址在构建前可达、构建中不可达，这三条证据把失败的位置锁定在中间件的运行时状态，而不是代码的逻辑。若不先排除这一层，直接把四条失败写成代码缺陷，后续的排查会从错误的方向开始，浪费的时间远大于一次日志核对。把环境的证据与代码的证据分开，是独立验收的基本要求。

缓存重建的选择也经过权衡。AOF 的增量文件已经损坏，`redis-check-aof` 虽然可以截断修复，但截断的位置与业务的写入时序无关，修复后的缓存可能出现半条记录或旧版本的状态。项目的 Redis 只承担实时状态的缓存，历史数据落在 MySQL，重建缓存的代价远低于带着一份不确定的缓存继续跑测试。备份目录的存在让这一步可以回滚，若后续发现缓存里有不可重建的内容，可以取回备份再另行处理。

第二，Mosquitto 的 1883 未监听。本批的测试不依赖 MQTT，构建与测试不受影响；如果后续要做 MQTT 链路的端到端验证，需要先补起 Mosquitto。

未覆盖的边界需要写成可执行的下一步，而不是一句笼统的「后续再看」。注入告警链路的验收需要三样输入：一个存在在飞订单的场景、一套启动完整的后端与中间件、以及一份按位移与电量分级的预期。三样输入齐备之后，验收的人可以按注入端点造出偏航与低电量，再按告警表与事件流核对级别与次数。这样的下一步让接续的人知道从哪里开始，也让未覆盖的项不会在交接中丢失。
