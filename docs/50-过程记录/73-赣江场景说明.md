## 1 场景概述

本场景聚焦赣江南昌段朝阳大桥至八一大桥之间的内河航段。

一艘货船正在该航段内向上游航行。航行途中，船上临时需要一票药品补给，但船舶无法立即靠岸采购。船员提交补给需求后，后端系统根据货物属性、船舶当前位置与未来轨迹、无人机能力、机巢位置、剩余电量、桥梁净空和实时风况等信息，判断订单是否可执行，并为订单选择合适的无人机和机巢，计算动态会面点和飞行航迹。

任务执行过程中，江面风速突然超过当前机型的抗风上限，并达到全域气象熔断阈值。系统依据任务安全复核结果，让原无人机放弃本次会面并携货返航。无人机返回机巢后，工作人员回收货物，订单重新进入调度队列，后端系统再根据新的状态决定是否重新调度。

本场景用于展示系统如何在移动船舶、有限运力、桥梁约束和突发风况下完成一次可解释的调度与安全处置。

Unity 三维演示独立运行，以 C# 复刻后端相同的算法逻辑和场景流程，不调用 Java 后端或 WebSocket。因此，三维画面中的计算不是后端实时结果。完成同一组测试输入的后端与 Unity 输出对照后，方可说明两者结果在约定误差范围内一致。

## 2 场景要解决的现实问题

内河货船在航行过程中不能随时停船靠岸。船舶靠泊通常需要联系码头、等待泊位并承担额外时间和费用，容易影响既定船期。

船舶航行途中可能出现以下补给需求：

- 船员临时需要药品；
- 船上淡水或生活物资不足；
- 船舶设备故障，需要紧急备件。

本阶段只选择其中一种需求作为主场景，即：

> **在航货船临时需要药品补给。**

选择药品作为主场景，是因为该需求时效性较强，能够清楚说明为什么船舶不能简单等待靠岸，也能够体现低空配送对移动船舶的价值。

传统小船接驳方式存在成本较高、耗时较长、受天气影响明显等问题。现有无人机配送又多以锚泊或相对静止的船舶为服务对象，难以直接处理持续航行中的移动船舶。

因此，本场景需要解决的问题是：

> 一艘货船正在赣江航行，船上临时需要药品，不能停船靠岸；系统能否在货船持续移动的情况下，判断是否可派、选择合适的无人机、计算会面位置，并在风况恶化时做出安全处置？

## 3 场景空间范围

### 3.1 服务航段

本场景将服务航段设置为：

> **赣江南昌段朝阳大桥至八一大桥之间的航段。**

该航段从南向北观察，依次经过：

```text
朝阳大桥
→ 南昌大桥
→ 八一大桥
```

按照本文桥梁坐标进行平面直线距离计算：

- 朝阳大桥至南昌大桥：约 **2.01 km**；
- 南昌大桥至八一大桥：约 **3.77 km**；
- 朝阳大桥至八一大桥全程直线距离：约 **5.78 km**。

上述数值是按给定经纬度作球面直线距离近似，不等同于船舶实际沿河道航行的里程。

如果首版演示需要缩短运行时间，可以暂时使用朝阳大桥至南昌大桥之间的约2.01公里直线航段；如果使用河道路径长度，应另行标注其来源。完整方案优先采用朝阳大桥至八一大桥之间的航段，以便展示更多航道约束和飞行过程。

### 3.2 桥梁约束

航段内涉及三座桥梁：

| 桥梁 | 纬度 | 经度 |
|---|---:|---:|
| 朝阳大桥 | 28.646 | 115.852 |
| 南昌大桥 | 28.663 | 115.859 |
| 八一大桥 | 28.692 | 115.879 |

上述坐标为公开地图上的示意坐标，原始坐标可能采用 GCJ-02。项目正式使用时，必须按照系统统一坐标基准完成转换，不得直接将不同坐标系的数据混用。

桥梁在本场景中的作用是提供真实的航迹约束：

- 无人机航线不能简单地穿过桥梁实体；
- 需要检查桥下可通行空间的高度、宽度和位置；
- 需要满足飞行高度和桥梁净空要求；
- 航迹规划应将桥梁作为路径可行性判断的一部分。

仅有桥梁中心坐标不足以支撑路径规划。首版搭建前还必须补齐每座桥的桥下可通行净空高度、桥墩开口位置、可通行开口宽度，以及与项目统一坐标系对应的几何表达。

本场景不要求对桥梁结构进行高精度三维测绘，但必须至少建立能够用于“可通行／不可通行”判断的简化几何模型，不能只放置一个桥梁坐标点。

## 4 场景参与对象

### 4.1 货船

场景中设置一艘内河货船，主要属性包括：

- 船舶唯一标识；
- 初始位置；
- 航行方向；
- 航速；
- 计划航迹；
- 当前状态；
- 关联补给订单。

货船持续向上游航行，不因等待补给而停船靠岸。

### 4.2 补给订单

场景中只设置一票药品补给订单，主要属性包括：

- 目标船舶；
- 货物类型：药品；
- 货物重量；
- 时效要求；
- 订单优先级；
- 订单创建时间；
- 订单当前状态。

首版演示不需要设置多种货物，也不需要同时展示多艘船。重点是把一票订单的完整生命周期讲清楚。

### 4.3 机巢

场景中在赣江两岸各设置一个机巢，共两个机巢。

机巢至少需要具有以下属性：

- 机巢位置；
- 可用无人机列表；
- 起降能力；
- 当前占用状态；
- 与服务航段的相对位置。

两个机巢的设置用于展示系统如何在不同起点之间进行候选方案比较，而不是简单选择距离船舶最近的无人机。

**机巢的具体经纬度尚未确定。** 在确定位置前，系统无法计算机巢到船舶的候选距离、动态会面点和返航路径，因此两个机巢坐标属于场景可计算化的前置输入，不得只用“江两岸各一个”的文字代替。

机巢坐标应在统一坐标系下配置，并记录坐标来源、机巢编号和坐标转换方式。若暂时采用演示假设坐标，应明确标注为仿真布点，不得表述为真实运营站点。

### 4.4 无人机

场景中设置2至3架能力存在差异的无人机。无人机可在以下属性上有所不同：

- 最大载重；
- 飞行速度；
- 剩余电量；
- 航程；
- 抗风能力；
- 当前所在机巢；
- 当前可用状态。

不同无人机的能力差异用于展示订单与机型匹配，以及“追得上”和“回得来”的可行性判断。

### 4.5 环境条件

场景环境至少包括：

- 赣江水面；
- 航道范围；
- 三座桥梁；
- 两个机巢；
- 货船；
- 无人机；
- 风速数据；
- 必要的禁飞或不可通行区域。

首版只注入一次风速突变，不开展连续风场仿真，也不要求接入真实气象服务。风速阈值分为两个不同用途：

1. **机型抗风上限**：用于调度侧与航迹侧判断某一具体机型在任务时段内是否可行。超过该机型上限时，淘汰该机型对应的候选方案。
2. **全域气象熔断阈值**：用于判断当前天气是否达到暂停新派单的条件。达到阈值时，系统停止新派单；在飞任务按既定安全策略处置，不把“停止新派单”直接等同于“所有在飞无人机立即返航”。

任务执行中的风速突变，应触发该机型任务安全复核；达到全域熔断条件时，还要触发全域停派。现有 G 组气象告警方案使用统一告警阈值，属于“是否产生气象告警”的检测口径；机型抗风上限属于“该组合是否可飞”的可行性口径，两者用途不同。全域熔断参数如何映射到当前 `sys_param` 与算法接口仍需项目组确认。

## 5 主故事流程

### 5.1 需求产生

货船正在赣江南昌段向上游航行。船员发现船上药品不足，且短时间内无法靠岸采购，于是提交药品补给订单。

订单进入系统后，系统首先检查：

- 目标船舶是否属于系统服务航段；
- 货物信息是否完整；
- 货物重量是否满足无人机运输条件；
- 当前是否处于气象熔断或其他禁止派单状态；
- 船舶状态和位置数据是否有效。

### 5.2 船舶预测

系统根据船舶当前的位置、航向、航速和航道约束，生成船舶未来轨迹预测。

预测结果至少包括：

- 未来轨迹点；
- 预计位置；
- 预计到达时间；
- 预测不确定性；
- 预测有效时间；
- 船舶是否仍沿既定航道运行。

### 5.3 候选方案生成

系统根据药品重量和时效要求，筛选符合条件的无人机，再结合两个机巢的位置和无人机实时状态生成候选组合。

候选组合可以表示为：

```text
具体无人机 + 所在机巢 + 目标货船
```

系统排除以下候选：

- 载重不足；
- 当前不在对应机巢；
- 正在执行其他任务；
- 处于故障、维护或失联状态；
- 预计无法在时间窗内追上货船；
- 完成投送后预计无法安全返回；
- 任务时段内风况超过该机型的抗风上限。

### 5.4 动态会面点计算

对于每个保留下来的候选组合，系统分别计算该组合对应的会面点和会面时间。

会面点由以下信息共同决定：

- 货船的预测轨迹；
- 货船航速和航向；
- 无人机所在机巢；
- 无人机飞行速度；
- 风况对有效飞行速度的影响；
- 桥梁和航道约束。

因此，会面点不是预先写死的固定坐标，而是某个具体“无人机—机巢—货船”组合的计算结果。

### 5.5 航迹规划与任务执行

系统在确定候选方案后，为无人机生成从机巢到会面点的可飞航迹。

航迹规划需要考虑：

- 桥梁位置；
- 桥下净空；
- 禁飞或不可通行区域；
- 目标会面点；
- 返航路径；
- 预估飞行时长和能耗。

系统确定起飞时间后，无人机从机巢起飞，沿规划航迹前往货船预计会面位置。

### 5.6 风速突变与安全处置

无人机飞行过程中，江面风速突然升高，并超过当前机型的抗风上限；如果同时达到全域气象熔断阈值，系统还应暂停新的派单。

系统收到气象数据后，先由监控侧产生气象超限事件，再由调度侧复核任务是否仍可安全继续。首版故事设定为复核结论“不宜继续本次会面”，执行以下处置：

```text
风速超限
→ 生成气象超限事件
→ 判断当前会面任务不宜继续
→ 放弃本次会面
→ 原无人机携货返航
→ 货物落地并完成回收
→ 订单重新进入调度队列
```

这里不应表述为“系统中途直接换机”或“另一架无人机接力”。

正确表述是：

> 飞行中不直接转移货物。只有原无人机返航并完成货物回收后，订单才具备重新调度和重新派机的条件。

### 5.7 后续重调度

货物完成回收后，系统根据最新的船舶位置、天气条件、无人机状态和订单时效，判断是否重新派单。

如果条件满足（包括风况已回落至全域熔断阈值以下），订单重新进入候选生成、可行性判断和方案择优流程；如果条件仍不满足，订单可以继续等待、转人工处理或被拒绝。

本场景的首版演示在“订单重新进入调度队列”处结束，不再展示新的可行方案和最终重派。

首版演示结束时必须注明当前状态：**风速仍处于全域气象熔断阈值以上，系统处于暂停新派单状态**，订单已具备重新调度的物理前提，但在风况恢复至阈值以下之前不会产生新的可执行方案。订单保持等待，待风况恢复后重新进入候选生成、可行性判断和方案择优流程。

“回收后重派完成”的完整过程由系统演示另行展示，不纳入本次三维演示首版。

## 6 场景中的核心约束

| 约束类别 | 具体内容 |
|---|---|
| 船舶约束 | 船舶持续移动，不能假设目标船固定不动 |
| 货物约束 | 药品重量必须满足无人机载重要求 |
| 动态会面约束 | 无人机必须在船舶运动过程中计算会面位置 |
| 返航约束 | 完成或中止任务后必须考虑返航电量和返航路径 |
| 桥梁约束 | 飞行航迹需要考虑桥梁位置、桥下净空和桥墩开口几何 |
| 机型气象约束 | 超过当前机型抗风上限时，该机型方案不可执行或需中止 |
| 全域气象约束 | 达到全域熔断阈值时暂停新派单 |
| 物理约束 | 已起飞货物不能直接转移给另一架无人机 |
| 资源约束 | 机巢、无人机和任务时段不能发生冲突 |
| 数据约束 | 坐标必须统一到项目规定的坐标基准 |

## 7 已知地理参数与待补数据

本节只记录场景涉及的已知地理参数和仍待补齐的数据。具体仿真取值不在本文定义范围内，由项目组按统一参数口径另行确定。

| 参数 | 首版值或状态 | 说明 |
|---|---|---|
| 服务航段 | 朝阳大桥至八一大桥 | 地理范围 |
| 桥梁点间直线距离 | 2.01 km、3.77 km、全程5.78 km | 按本文坐标计算；不是河道里程 |
| 三桥桥下净空高度 | 待核实 | 需可靠地图、测绘或公开工程资料 |
| 三桥桥墩开口位置与宽度 | 待核实 | 需形成路径规划可消费的几何数据 |
| 两岸机巢坐标 | 待配置 | 未确定前不能完成真实距离、会面点和返航路径计算 |
| 坐标基准 | 待与系统统一坐标口径确认 | 输入坐标需转换后再参与计算 |

**几何数据验收门槛：** 每座桥必须有可通行开口的水平范围和净空高度；每个机巢必须有统一坐标系下的位置。上述数据未补齐时，可以做视觉展示，但不得声称已经验证桥梁净空路径规划或真实机巢选址下的可达性。

## 8 场景与现有项目系统的对应关系

| 场景环节 | 对应项目能力 |
|---|---|
| 船员提交药品需求 | 下单页、订单接入 |
| 判断船舶是否进入服务航段 | 接单判断 |
| 预测货船未来位置 | 船舶状态估计与轨迹预测 |
| 根据药品属性筛选无人机 | 候选机型、机巢和无人机生成 |
| 判断能否追上和返回 | 候选组合可行性判断 |
| 计算动态会面位置 | 会面点求解 |
| 生成经过桥梁约束的航迹 | 可飞航迹生成 |
| 监控无人机状态和风况 | 飞行任务监控 |
| 识别风速超限 | 气象超限检测 |
| 决定放弃会面和返航 | 飞行过程中的重新调度、返航复核 |
| 货物回收并重新进入调度 | 货物状态机、订单状态机、重调度流程 |
| 展示轨迹、会面点和异常事件 | 可视化大屏与时间轴回放 |

## 9 三维演示的实现边界

### 9.1 三维演示的定位

三维演示是项目的汇报素材，不是现有业务系统的正式模块。

它的作用是：

- 将赣江南昌段的地理环境具体呈现出来；
- 让评委看见货船、无人机、机巢和桥梁之间的空间关系；
- 将动态会面、桥梁约束和风速突变等过程可视化；
- 为项目汇报提供一段可重复播放的场景演示。

三维演示不应被表述为已经接入真实无人机或真实水面运行系统。

### 9.2 演示技术方案

三维演示可以采用以下方式搭建：

- 使用 Unity 作为三维场景运行环境；
- 使用 Cesium 或其他地理数据工具提供赣江南昌段地景；
- 建立桥梁、货船、无人机和机巢的低精度模型；
- 使用 C# 脚本驱动模型运动和异常事件；
- 在场景内部生成仿真数据并完成一条可回放流程；
- 提前固定航段、机巢位置、相机路径和事件时间；
- 录制独立视频，作为现场汇报的备用素材。

三维演示首版独立运行，不调用现有 Java 后端或 WebSocket 数据流。Unity/C# 侧复刻动态会面、候选判断和异常处置所需的同一套算法逻辑，并以固定测试输入与 Java 后端结果进行对照，记录误差和容差。未完成对照测试前，只能称为“算法逻辑复刻的独立仿真演示”，不能称为“后端实时计算结果”或“结果已证明一致”。

### 9.3 三维模型要求

模型不追求写实，重点是让评委看清：

- 物体的位置；
- 物体的朝向；
- 无人机的飞行方向；
- 货船的行驶方向；
- 机巢的起降位置；
- 货船甲板上的交接位置。

优先保证空间关系、运动过程和约束效果清晰，避免因过度追求模型精度影响录制和播放稳定性。

## 10 演示验收标准

三维演示至少应让评委看到以下内容：

1. 赣江南昌段和三座桥梁的空间环境；
2. 一艘货船沿航道向上游航行；
3. 两个机巢和2至3架无人机；
4. 一票药品补给订单；
5. 无人机从机巢出发并前往动态会面点；
6. 会面点不是固定坐标，而是由场景参数计算得到；
7. 飞行航迹体现桥梁实体对航线的约束；
8. 风速突然超过当前机型的抗风上限，必要时达到全域气象熔断阈值；
9. 无人机放弃本次会面并携货返航；
10. 货物回收后，订单重新进入调度流程并进入等待状态，待风况恢复至熔断阈值以下后重入候选生成与方案择优；
11. 演示过程中不出现飞行中直接换机或空中接力的表述；
12. 明确说明当前为仿真演示，不等同于真实水面运营。

## 11 统一对外表述

### 11.1 一句话版本

> 我们聚焦赣江南昌段一艘在航货船的药品补给需求，验证系统在移动船舶、桥梁约束和突发风况条件下，能否完成动态会面、飞行调度和安全返航处置。

### 11.2 申报书版本

> 本项目以赣江南昌段朝阳大桥至八一大桥之间的在航货船药品补给为仿真示范场景。针对货船无法随时靠岸、目标持续移动以及内河桥梁和气象条件对飞行任务造成约束等问题，后端系统根据订单属性、船舶轨迹预测、无人机状态、机巢位置和航道限制，完成候选方案筛选、动态会面点求解和飞行航迹规划。独立三维演示由 Unity/C# 复刻相同算法逻辑并以仿真数据呈现，不是后端实时驱动。当风况触发当前机型的安全处置条件时，原无人机放弃本次会面并携货返航；货物完成回收后，订单重新进入调度队列，并在风况恢复前保持等待，不宣称完成最终重派。该场景用于验证核心调度逻辑在有限仿真条件下的可行性，不代表当前已经完成真实水面运营。

### 11.3 答辩口语版本

> 我们没有把项目直接包装成已经覆盖整个内河物流，而是先选择赣江南昌段的一段具体航道，模拟一艘正在航行的货船临时需要药品补给。后端算法要回答三个问题：哪架无人机能够追上这艘船、在哪里与它会面，以及遇到突发风况后如何安全处置。三维演示由 Unity 独立运行，复刻同一套算法逻辑并用仿真数据呈现，不是后端实时驱动。风况触发安全处置条件时，原机携货返航，货物回收后订单再重新调度。我们通过系统结果和三维回放展示这个有限场景下的算法流程。

## 12 场景边界与后续扩展

### 12.1 当前不纳入首版场景

- 多艘货船同时调度；
- 多票订单并发；
- 真实药品配送；
- 真实无人机飞行；
- 真实水面测试；
- 连续三维风场仿真；
- 飞行中空中换机；
- 空中货物接力；
- 真实飞控链路接入；
- 生产级高并发和全域运营。

### 12.2 后续可扩展方向

- 将药品扩展为淡水、备件和生活物资；
- 增加多艘船和多票订单；
- 增加多机巢协同调度；
- 增加低电量、失联和临时空域限制等异常；
- 接入真实 AIS、气象和水文数据；
- 将三维演示与正式系统的仿真数据接口打通；
- 进一步开展真实水面测试。

## 13 最终场景定义

本项目当前阶段的具体应用场景可以最终定义为：

> **在赣江南昌段朝阳大桥至八一大桥之间，一艘正在向上游航行的货船临时需要一票药品补给，但无法停船靠岸。后端系统从两岸机巢和多架无人机中筛选可行方案，结合船舶轨迹预测、桥梁约束和风况条件计算动态会面点并规划航迹。任务执行过程中，风况触发当前机型的安全处置条件，系统让原无人机放弃本次会面并携货返航；货物完成回收后，订单重新进入调度队列，并在风况恢复前保持等待。Unity 三维演示独立复刻同一算法逻辑并呈现仿真过程，不代表后端实时计算或真实水面运营。该场景用于验证系统在移动船舶和突发环境变化下的调度与安全处置能力。**
