## 二 本次代码改动

`OrderRequeueCommand` 的规范构造器此前只拦截「灭失 + 落巢」与「灭失 + 回收」两种矛盾态，遗漏「未落巢 + 已确认回收」。按 `21` §8 货物回收的物理前置，货物只有随原机成功落巢后才可被回收为可用，因此该组合在物理上不成立，须在 record 边界拒绝，不能只靠 `RescheduleService` 下游兜底，因为其他消费方会静默接受不可回收货物。

```java
if (!landedAtNest && recyclingConfirmed) {
    throw new IllegalArgumentException(
            "回收确认与落巢冲突：货物须随原机成功落巢后才可被回收为可用（《21》§8）");
}
```

同步调整测试：原「野外迫降 + 已人工回收」用例改为构造期即拒绝，用例名为 `requeueOrder_shouldRejectFieldRecoveryClaimAtConstruction`，断言消息点明缺落巢前提；其余 12 个用例保持通过。
