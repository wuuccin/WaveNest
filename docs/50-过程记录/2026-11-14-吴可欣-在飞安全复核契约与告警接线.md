## 1 本次的三项

本段依据 11-14 任务清单的三项：序号 1-1 的气象超限到在飞安全复核的接口定义、序号 2-1 的评审缓置实修四条、序号 2-2 的在飞安全复核生产接线。

## 2 序号 1-1 的契约

契约落在 `wl-m2-dispatch` 的 `dispatch/reschedule` 包，新增三个类，`RescheduleService` 当时加了一个方法。

### 2.1 触发来源

`InflightSafetyTrigger` 定义五个来源，逐字对齐 `84-E组算法方案` 第 7.3 节的 `trigger_source` 五值：意图变更、G 组告警、电量包线破限、失联超时、空域或气象。本批只接「空域或气象」一值，其余四值先定义、不接线，避免后续加值时牵动已经合入的调用方。

### 2.2 请求字段

`InflightSafetyRequest` 有九个字段：`eventId`、`trigger`、`orderId`、`droneId`、`windSpeedMs`、`alertLevel`、`durationSec`、`observedAtMs`、`cleared`。

`orderId` 允许为空，为空时由调用方按 `droneId` 反查在飞订单。`durationSec` 传负数按 0 处理。`eventId`、`trigger`、`droneId` 为空的，构造时直接抛异常。`windSpeedMs` 是基本类型，风速缺失时调用方要传 `Double.NaN`，不能传 0，因为 0 是合法风速，会判出一个建立在假数据上的结论。

### 2.3 结论三值

`InflightSafetyVerdict` 有三值：`CONTINUE` 表示继续，`ADJUST` 表示调整，`TERMINATE` 表示终止。每值带一个写入 `task_log` 的 `op_type`，分别为「在飞安全复核-继续」「在飞安全复核-调整」「在飞安全复核-终止」。

### 2.4 判档规则

判档按序命中：`cleared` 为真时判继续；级别为严重时判终止；其余情况判调整。判档的唯一源是 `InflightSafetyVerdict.judge`，它是纯函数、无 IO。`review` 返回空表示「没判」，不表示「判过且安全」。风速非有限或为负、级别不属于警告与严重、观测时刻不合法、入参为空，都返回空，调用方不得据此放行。

`alertLevel` 使用 `AlertLevel` 枚举，取值是提示、警告、严重，不使用字符串。这一层不比对 8.0 与 14.0，也不看机型抗风上限，阈值的判定在 M4 的检测器里。终止档在 11-14 当时不改订单状态，11-15 的收口改为在功能 10 有可执行落点时回写「返航中」，详见本文第 6 节。

## 3 序号 2-2 的生产接线

新增 `InflightSafetyService`，对外只有一个方法：

```java
Optional<InflightSafetyVerdict> review(InflightSafetyRequest request)
```

它自己查订单，`orderId` 为空时按机号反查；只认去程中与末段交接中两种状态，其余状态返回空；写 `task_log` 留痕；终止档调用功能 10 做中止返航；事务外广播订单状态事件。

请求由告警消息组装，九个字段的对应关系如下：

| 请求字段 | 告警消息来源 |
|---|---|
| `eventId` | `message.eventId()` |
| `trigger` | `InflightSafetyTrigger.AIRSPACE_OR_WEATHER` |
| `orderId` | `message.orderId()`，可以为空 |
| `droneId` | `message.droneId()` |
| `windSpeedMs` | `message.currentValue()`，为空时传 `Double.NaN` |
| `alertLevel` | `AlertLevel.fromValue(message.level())` |
| `durationSec` | `message.duration()` |
| `observedAtMs` | `message.timestamp()` |
| `cleared` | 恒填 `false` |

`cleared` 恒填 `false` 的原因是 M4 的解除只做内存复位、不投 `alert.event`，M2 收不到解除消息。级别为「提示」时返回空，气象超限正常只有警告与严重两档，出现提示级要先查检测侧。

## 4 序号 2-2 的调用点

`AlertDrivenDispatcher.route` 里，气象超限分支由序号 2-3 的宋冰鑫改为调用 `InflightSafetyService.review`：先 `claimEvent` 去重，再组装请求，再调 `review`，最后在 `finally` 里 `releaseEvent`。`LINK_ERROR` 留在原地。本记录只记调用关系，具体实现见宋冰鑫的同日记录。

一条告警对应一架无人机，检测侧按机逐条出，每架一个 `eventId`，M2 侧不写循环。`review` 不做 `eventId` 去重，复用调用方的 `claimEvent` 与 `releaseEvent`。

## 5 序号 2-1 的台账实修

第一，`OccupancySlotService` 的 `activeSlots` 与 `findActiveSlotByOrder` 都补了「结束时刻晚于当前」的条件。以前只按状态等于有效查询，过期占位照样返回。`findActiveSlotByOrder` 的修改改变了流程：`CargoNestGate` 用它判断「本单已锁巢」，命中就跳过 `tryReserve` 直接放行。过期锁被当真，等于压根没锁还放行。修好之后，这类订单会重新走 `tryReserve`，巢占满时出现 `WAIT_RESOURCE`，这是正确行为。

第二，`RendezvousCoordinator` 与 `FlightPhaseChangedEvent` 的两条实修补齐。

第三，另外五条只改注释，不动行为。`FlightPhaseChangedEvent` 第 18 行与 `OrderRequeueCommand` 第 37 行两条维持缓置，理由写在原处。

第四，`GateController` 的鉴权缺口只写明「无鉴权仅限内网演示」的边界，不引入权限体系、不加来源白名单。来源白名单统一由序号 2-10 在实时通道配置里落地。

## 6 11-15 的收口

11-15 的 `e12dfb2` 对这条链做了四项收口，本记录按最终状态写：

1. 删除 `RescheduleService.evaluateInflightSafety`。它在全仓零调用、零测试引用，生产入口只有 `InflightSafetyService.review`。1-1 当时留两个入口，会让下游跳过订单存在性与在飞状态前置。
2. 终止档在功能 10 有可执行落点后，同一事务内条件更新 `order_task.status` 为「返航中」，写迁移行并补发 `OrderStateChangedEvent`。迫降野外由功能 10 置「失败」，本层不覆盖；功能 10 返回空时只留审计。
3. `23-状态机定义` 升 v0.8，第 8 节补订单「去程中 → 返航中」一行，并把回收重派的前态改为已派发、去程中、末段交接中、返航中四态。
4. `29-各组算法层接口定义` 的 C-11 与 `84-E组算法方案` 的 A2.3 补严重阈值档的例外句。

## 7 验证

`wl-m2-dispatch` 的全量测试在 11-15 的收口后为 575 项 0 失败。`InflightSafetyServiceTest` 覆盖了告警未带单号按机号反查、级别为提示时返回空、终止档回写、迫降野外不写「返航中」等路径。`AlertDrivenDispatcherOrderLookupTest` 是仓库里唯一直接构造 `AlertDrivenDispatcher` 的地方，本次补了 mock 字段与构造参数，并追加三个气象用例。

## 8 边界与已知简化

第一，气象告警不带机位。`AlertEventMessage` 的 `lon` 与 `lat` 在组装请求时没有进九个字段。本批以订单会面点作为当前位置与返程起点，它是在飞无人机「该到的点」，用它算返程距离偏大，属保守侧。订单没有会面点时，不执行功能 10，只留审计，不臆造坐标。

第二，风况快照传 `null`，按 `84` 第 7.3 节的「无风况快照则按固定裕度系数 k 判」降级，不伪造风值。

第三，本批不新增鉴权体系，不新增来源白名单。实时通道的来源限制由序号 2-10 落地。
