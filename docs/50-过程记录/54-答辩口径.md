## 1 讲什么、不讲什么

主讲按演示主线（`55` v0.5 七段）逐段对齐，每段都有画面可指、都有系统内证据（见 §6）：

| 级别 | 环节（对应 55 七段） | 核心说法 |
|---|---|---|
| 主讲一 | 下单与预计会面（第 1 段） | 会面点是动态算出来的组合级产物，不是先画好的固定坐标 |
| 主讲二 | 首机去程（第 2 段） | 追得上、送得到、回得来，在派单前就已证明；追不上或回不来的组合在派单前就被剪掉 |
| 主讲三（高光） | 风速突变（第 3、4、5 段）：标尺指针跃升、告警实体闪烁、事件流追加 → 在飞安全复核 → 原机放弃会面携货返航 | 风变了不硬撑：先停新派单，再对在飞任务做安全复核，结论不宜继续就回上游重走 |
| 主讲四（分水岭） | 回收与重入队（第 6 段） | 不中途换机——货物回收后重派，这是与「空中接力」说法的分水岭 |
| 主讲五 | 收口加演（风况回落 → 熔断解除 → 重派交接） | 处置是闭环：风停、闸门开，新机按同一套择优规则接手直至完成 |
| 带过 | 接单判断、航线规划内部细节、预测算法内部 | 一句带过，不占主讲时长；被追问技术细节才按 §3 展开 |
| 不宣称 | 已验证桥梁净空、真实水面运营、中途换机／空中接力、多级改投 | 主动说边界，比被拆穿可信（见 §5 话术纪律） |

预测驱动与可达性剪枝仍是技术主线，但讲法必须挂在演示段上：先指画面，再讲机理，不脱开演示空讲卖点。

## 2 主讲顺序与一句话兜底

主讲按演示段推进：下单与预计会面 → 首机去程 → 风速突变高光 → 回收重入队 → 收口加演。每段等系统内确认再开口（通过条件见 `55` §2.1／§2.2），画面没跟上就不抢话。

一句话兜住全场：

> 「在船进入服务航段之前，就用轨迹预测算出会面点，并在派单前证明这一单追得上、送得到、回得来；风变了不硬撑——复核、返航、回收，等风况回落、熔断解除，再由新机重新派发完成交接。」

## 3 高频追问标准答案

| # | 追问 | 标准答案 |
|---|---|---|
| 1 | 船突然掉头了怎么办？ | 这不是纠偏能解决的，我们判定为意图变更，回到可达性判断重新走一遍。能说出「回上游重走」而不是「继续微调」，说明清楚预测的边界，比硬撑「我们预测很准」更可信 |
| 2 | 会面点是怎么算出来的？ | 不是先算一个全局会面点再去挑机——求会面点需要速度和起飞点，这两者只有具体到「哪架机、从哪个巢」才确定。所以会面点是每个候选组合自己算出来的，属于剪枝的产物之一，不是剪枝的输入 |
| 3 | 多机多单怎么分？ | 先预测、再剪枝淘汰、后择优；中选后占住机、巢位、会面窗口、归巢时隙，冲突顺延次优；起飞时刻在航迹精算后回填，航迹级冲突优先错峰 |
| 4 | 会面交接时还追踪吗？ | 全程都在追踪，交接时更在追。追踪是横切线不是步骤；变的只是控制目标——去程段追「船未来会到哪」，末段追「我与船此刻相对怎样」。进入会面点邻域后不再重算会面点，改为保持相对静止并完成交接 |
| 5 | 中途出问题，能换一架机接着送吗？ | 不能，而且这正体现了想清楚了。货物是有限对象，离巢后就绑在那一架机上，此时派任何别的机都拿不到货。正确处置是让原机带货返航或迫停 → 货物落巢回收 → 订单重入队重派。能主动说出「换机的前提是货物先回到系统」比回答「支持中途换机」更有说服力 |
| 6 | 派单时就算过电量，返航为什么还要再算？ | 两次性质不同：派单时是预测（按预计风况与航线估），返航前是事实（按实际剩余电量与实时风况复核）；复核不过则申请应急迫停，需按占用时间窗判定准入，无位可借才转应急迫降点 |
| 7 | 装货不要时间吗？ | 装机耗时在首版显式取 0，理由已写进设计：该耗时相对飞行时长与船舶等待时间量级很短；偏乐观造成的偏差由去程段持续纠偏吸收；若实测表明不可忽略，它会作为一个可配置参数重新引入 |
| 8 | 并发是怎么控的？ | 不用「来一单派一单」的流式派发，而是建立全局资源占用台账，并在批处理窗口内做订单与资源的全局匹配——这避免了先到先得的贪心次优；高优先级订单走快速通道保证时效。对飞行中的重规划请求做分级流量治理：安全相关告警不可丢弃并优先处理，常规纠偏可合并、可延后，超出处理能力的直接降级为维持原航迹。因为**过时的决策比不做决策更危险**，这保证系统在任何负载下都能维持基本的监控与兜底能力。（可补一句「类似网约车派单的攒批匹配」） |
| 9 | 机位判断与别家有什么不同？ | 多数方案的机位判断是静态计数——「还有没有空位」；本项目做到时间窗维度——「借出去的这段时间里，会不会把原驻机挤掉」。它与第 5 步精算后的占位复校是同一套思想：**占位是时隙，不是布尔** |
| 10 | 系统加了多少锁？ | 应讲「统一台账」。真正的设计是「登记哪些资源、占用多久、何时释放」，锁只是保护台账的工具；只讲加锁会显得停留在工程细节层面 |
| 11 | 风况变化你们怎么知道的？ | 江面风况按网格点逐点进系统（每个位置、每个时刻各一条），画面标尺只画系统实测值、不造默认值；风况回落与熔断解除都以系统内观测和闸门状态为准，不以口头报数替代 |
| 12 | 熔断解除为什么要等几秒？ | 解除要求连续多条观测都低于严重阈值（防抖），防止阵风在阈值边缘反复通断；解除后由后台把熔断期间积压的订单逐单唤醒重入队，不靠人工再点一遍 |
| 13 | 重派的新机是谁挑的？ | 和第一次派单同一套规则：重新展开候选组合、按可行性与时隙占位择优。新机不是指定的接班机，而是重新比较出来的最优解 |

## 4 货巢前置决策与讲法顺序

货巢是下单时刻按船位与机巢台账先定的前置决策，不进剪枝漏斗；进入已定货巢后，才在「已定货巢 × 机型 × 实例」里逐台核追得上、回得来。新口径下对外讲法与内部顺序一致：

| 场景 | 采用的顺序 | 说明 |
|---|---|---|
| 代码实现、算法设计 | 下单先按船位与机巢台账定货巢 → 已定货巢内机型 → 实例 | 货巢是下单时刻的前置决策，不进剪枝漏斗；进入已定货巢后仍逐台核追得上、回得来两关 |
| 流程图、答辩表述 | 船在哪、定哪个货巢 → 调什么机型 → 派哪一架 | 更符合听众直觉，也与内部决策顺序一致 |

被追问「这个巢够得着吗」时，答「货巢是下单时按船位和机巢台账先定的；进到这个货巢内部，再逐台核机型和实例的追得上、回得来。够不着就在已定货巢内换机型或实例，或按新的船位重选货巢，不是靠机型先把巢筛掉」。

## 5 话术纪律

1. **对外表述按 `02-术语表` §6 的去算法化映射**，算法名词只在被追问技术细节时展开。
2. **禁用**「改派」「接力」「由下游接手」，统一说「货物回收后重派」。
3. 不承诺本期范围外的能力：接力交接（空中换机）、货物转运、多级改投、空中排队等待、下游同品库存补送。
4. 讲「时间窗占位」而不是笼统的「占位」；讲「统一台账」而不是「加锁」。
5. 不把讲法写回设计文档：星级、卖点、讲法只存在于本文与 `55-演示剧本`。
6. 演示证据只摆系统内落库记录（见 §6 证据表）；录屏与画面截图是讲解辅助，不作为「已验证」的替代证据。净空数据补齐前不说航迹规划已满足净空约束。

## 6 主讲环节的系统内证据（按摆出顺序）

| 主讲环节 | 系统内证据 | 出处 |
|---|---|---|
| 下单与预计会面 | `order_task` 订单行（含 `meet_time` 会面时刻）；`rendezvous` 帧（十字准星）；派发摘要的 `task_log` 行 | 派发编排按会面方案落 `order_task.meet_time`；会面方案提交事件转 `rendezvous` 帧 |
| 首机去程 | `order_task.status`「已派发 → 去程中」迁移行；`plan_track` 三段航迹帧；`flight_point` 实测航点 | 飞行阶段推进器逐段写 `task_log` 与订单状态；遥测实测点落 `flight_point` |
| 风速突变（高光） | `weather` 帧逐网格点观测（气象标尺唯一来源）；`alarm` 帧「气象超限」；在飞安全复核一条 `task_log`（`op_type` 为继续／调整／终止中文词）；终止档另有一条「原状态 → 返航中」迁移行（两条 `op_type` 语义不同，勿合并出示）；复核结论随 `order_state` 帧的 `safetyReview` 带出 | 复核结论写 `task_log`，审计本身不是状态迁移；终止档才追加返航迁移行 |
| 回收与重入队 | 回收确认消息落库（货物状态转「已回收」）；`order_task.status` 回「待调度」迁移行 | 回收消息由 M2 消费落库；重入队回到「待调度」 |
| 收口加演 | `weather` 帧风速低于预警阈值 8.0 m/s；派单闸门摘要「熔断中 → 正常」；新机订单行（执飞机号不同于原机）经「已派发／去程中」「末段交接中」至「已完成」 | 闸门为内存状态机，以 REST 快照与帧为准；重派仍走候选择优链 |
