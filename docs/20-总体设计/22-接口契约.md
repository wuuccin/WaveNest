## 1 消息主题与统一信封

### 1.1 统一信封

模块间异步消息一律用同一信封封装：

```
ParsedMessage { sourceId, type, ts, payload }
```

| 字段 | 含义 |
|---|---|
| `sourceId` | 来源标识（数据源或模块） |
| `type` | 消息类型，决定下游走哪套处理逻辑 |
| `ts` | 打点时间 |
| `payload` | 结构化对象，字段见 §2 |

### 1.2 MQ 主题

| 主题 | 内容 | 生产方 | 消费方 |
|---|---|---|---|
| `raw.ais` | AIS 船位原始报文 | M1 | M1 内部（解码） |
| `raw.uav.telemetry` | 无人机遥测原始报文 | M1 | M1 内部（解码） |
| `raw.weather`、`raw.hydro`、`raw.notice` | 气象、水文、公告原始数据 | M1 | M1 内部（解码） |
| `data.ais` | 解析后的船位对象 `AisMessage` | M1 | M2、M5 |
| `data.uav.telemetry` | 解析后的遥测对象 `UavTelemetry` | M1 | M4、M5 |
| `data.weather` | 解析后的气象对象 | M1 | M2、M3、**M4**、M5 |
| `data.hydro`、`data.notice` | 解析后的水文、空域公告对象 | M1 | M2、M3、M5 |
| `alert.event` | M4 的异常告警（与 WebSocket 双推） | M4 | M2、M5 |
| `task.plan` | 任务方案（机、巢、会面点、起飞时刻、航迹、船舶预测轨迹） | M2 | M4 |

约定：

1. 主题名按四类前缀分区：原始 `raw.*`、解析后 `data.*`、告警 `alert.*`、任务方案 `task.*`（具体主题名见上表）。
2. **遥测只接入一次**：`data.uav.telemetry` 由 M1 生产，M4 不另建订阅链路；上行指令由 M4 编码后经 M1 的 MQTT 通道下发。
3. 投递失败按策略重试，超过阈值转死信隔离，不影响主流程。
4. **M6 不作为 MQ 消费方**：落库与入缓存由 §5 的 `M1 → M6` 调用完成，故 `data.*` 的消费方只列 M2、M3、M4、M5。
5. **主题名以本节为唯一权威**：各模块不得自造 MQ 主题，一律引用本节；全项目 MQ 基调为 **MQTT（遥测／指令链路，由 M1 建链）＋ RabbitMQ（业务消息）**，不引入 Kafka（见 `30-M1-数据采集` §5 类名裁决 C3）。

### 2.1 算法层对象 → 模块层落点投影（M-3）

算法层对象（`80`–`86`）与模块层对象（`30`–`38`）**不是一回事**：`ship_traj` 等 WS 载荷只是算法层全对象的**子集**。为避免下游把子集当全对象用（如 E 组功能 17 的 NIS／σ 缩放判据缺 `zSeries`／`calibrationFactor`），落点投影统一如下（详表见 `80` §2.8、`29` §1.2）：

| 算法层对象 | 模块层落点 | 投影关系 |
|---|---|---|
| `PredictionSnapshot`（全字段） | Redis `ship:pred:{mmsi}` | 完整对象，无损 |
| `PredictionSnapshot` | WS `ship_traj`（§4） | **子集**，缺 `zSeries`／`deviation`／`enterTimes`／`branchId`／`calibrationFactor` |
| `PredictionSnapshot` | `task.plan` 内嵌船舶预测轨迹 | 子集，供 M4 偏差比对 |
| `AdmissionResult` | `order_task.status` ＋ `task_log` | 只投影状态与原因码 |
| — | **不得落到 `ship_ais`** | U-04：`ship_ais` 只存 M1 的原始 AIS值 |
| `B_RendezvousSolution` | `task.plan` 内嵌会面点＋时间窗；M4 只取坐标与时刻 | **子集**：只投影 `meetLon`／`meetLat`／`meetTMin`／`meetTMax`；`τ_coarse`、`snapshotVersion` 不下发 |
| `B_FlyableRoute` | `task.plan` 内嵌无人机航迹；M4 照它执行 | **子集**：只投影 `waypoints` ＋ `routeVersion`（重算比对用）；精确能耗、路径风险、迫降点标注不下发 |
| `B_TakeoffTimeResult` | `task.plan` 内嵌起飞时刻 | **子集**：只投影起飞时刻与「是否不可行」结论 |
| `B_ConflictResult` | 不下发（组内） | 纯 D 组内决策产物；`checksumVersion` 指向 `B_FlyableRoute.routeVersion`，不外发 |
| `B_ReturnRoute` | M2 返航决策内部使用；**不进 `task.plan`** | 返航在起飞后才产生，不属任务方案载荷；E 组经 M2 常驻层按需取，不走 WS |
| `B_HandoverConfirmation` | M2 状态更新；G 组功能 19 经 M2 取 | 实际会面点、交接时刻、伴飞与交接开销随 M2 内部流转；`plannedMeetLon`／`plannedMeetLat` 是 G 组 `d_space` 的比对基准，**须原样保留** |

### 2.1.1 不确定度与标定因子的对外约定（C-01，A 组 → E 组）

**对外交付的是「标准差标量对 ＋ 主轴方位」，不是经纬度 2×2 协方差矩阵。** 定义处 `80` §2.3、§2.6：

| 量 | 字段 | 单位 | 说明 |
|---|---|---|---|
| 纵向不确定度 | `sigmaAlong`（`points[i].sigmaAlong`） | m | 沿航迹方向 |
| 横向不确定度 | `sigmaCross`（`points[i].sigmaCross`） | m | 法向 |
| 主轴方位 | `courseDeg` | 度 | 旋转角，`ψ = courseDeg` |
| 标定因子 | `calibrationFactor` | — | 由 NEES 一致性检验标定的带宽修正 |

- **需矩阵时按下式重建**：`Cov = R(ψ) · diag(sigmaAlong², sigmaCross²) · R(ψ)ᵀ`，`R(ψ)` 为按主轴方位旋转的标准旋转矩阵。
- **消费侧判据（强制）**：下游须判 `NIS₂ / calibrationFactor`，或改用 `k · σ`。依据 `80` §2.6 跨组裁决 A-1、A-6——A 组交付的是**含模型误差项的保守包络**而非滤波器预报协方差，`NIS₂` 系统性偏小，不除 `c` 会显著偏保守。
- **C-01 关闭**：形式由 A 组定（`80` §2.6），E 组确认按此消费（`84` §6 与附录一均按标准差对＋方位实现口径），本文 §4 `ship_traj` 的 `cov` 已写明**标准差非方差**，单位一致。

## 4 WebSocket 消息

推送型接口，统一格式：

```json
{ "type": "...", "data": { ... } }
```

`type` 决定前端走哪套渲染逻辑。`36-M5-可视化` §3「算法输出到画面的映射」对照表，依赖下列消息：

| `type` | 数据内容 | 前端渲染 |
|---|---|---|
| `ship_traj` | 船舶未来轨迹点列 ＋ 不确定性 `cov`（**标准差，非方差**；椭圆半轴取 `a = 2·sigmaAlong`、`b = 2·sigmaCross`，旋转角 `courseDeg`，见 `80` §2.3、`29` §3.3）+ `version`、`t0`、`courseDeg`、`validitySec`、`premise`（字段全量见 `80` §2.3、§2.8，本条只收模块层载荷子集） | 虚线轨迹 ＋ 半透明置信椭圆 |
| `drone_state` | 无人机位置、电量、飞行阶段 | 机位图标与状态卡 |

| 第 7 步 | M3 → M2 | 交接成功确认 | M2 更新任务状态，M4 记录投送结果 |
| 第 7 步 | M3 → M2 | 交接失败上报（重试、悬停等待均失败后） | M2 决定返航或转应急迫停 |
| 第 8 步 | M2 → M6 | 按实际剩余电量与实时风况复核；向他巢申请应急迫停的准入判定 | 落点：原驻巢 / 迫停巢 / 应急迫降点 |
| 第 8 步 | M2 → M3 | 生成返航航迹（无人机当前位置 → 落点） | 返航航迹 ＋ 返程电量与到达时刻 |
| 第 8 步 | M2 → M6 | 释放占位、更新无人机与订单状态、写流转日志 | — |
| 第 8 步 · 回收与重派 | M2 → M6 | 落巢后写货物「已回收」及其当前载体与位置；订单重入队（状态回到待调度） | 货物转为可用，订单重新走第 2、3、4 步（闭环见 `21` §8；货物状态写入方见 `37` §2） |
| 横切 · 实时追踪 | 船侧：M1 → M2；机侧：M1 → M4 → 共享数据源（**共享数据源由 M4 写入清洗后的遥测**，见 `34-M4` §2.1.3、`21-主流程设计` §6） | 清洗后的状态 | M2、M3、M5 按需取用 |
| 横切 · 兜底 | M4 → M2 | 异常上报（航线偏离、低电量、失联、通信中断） | M2 决策 → M3 执行改航或退避 |
| 数据回流 | M4、M3 → M2 | 实际能耗、实际会面偏差、轨迹预测误差 | 校准能耗模型、纠偏阈值与策略偏好、预测模型参数 |

三条契约层的硬约定：

1. **M2 是唯一调度主控**：M3 只在被调用时求解，不主动发起（**例外澄清**：`33-M3-路径规划` §3.5 的去程纠偏循环是常规流程内的**持续循环体**，由「每收到一次新状态（新遥测）」触发，**不视为「主动发起」**；其循环内求解仍经调用 TP（M2 常驻层）与 `32`，6b 一律上报 M2）；M4 只检测与上报，不判断可行性。
2. **闭环只经 M2 闭合**：飞行中改方案一律 M3／M4 → M2 → 重跑，不允许旁路。
3. **「船舶大幅变向或减速」这条兜底与 6b 是同一条链路**，实现复用，不设计两套。

## 6 时序消息清单（跨模块）

> 本节参与者跨 M2／M3／M4：DP（调度引擎）、TP（轨迹预测）、SE（态势估计）属 M2——预测与状态估计都是常驻层产物，M3 不自建预测主体（`32-M3-动态会面` §2）；RS（会面求解）、RP（航迹规划）属 M3；FC（飞控）属机载执行侧，只执行与回传实况，判定归 M3。早期把本节称作「M3 内部」不准确，已订正。

`32-M3-动态会面`、`33-M3-路径规划` 与 M2、M4 的协作参与者：

| 代号 | 参与者 |
|---|---|
| DP | 调度引擎 |
| TP | 轨迹预测 |
| RS | 会面求解 |
| RP | 航迹规划 |
| SE | 态势估计 |
| FC | 飞控 |

消息流（按四段 ＋ 收尾）：

| 段 | 消息 |
|---|---|
| 求会面点 | DP → TP 请求该船未来轨迹；TP → SE 取船舶当前状态与航道拓扑约束；SE → TP 回船位、航向、航速（信号缺失时沿航道外推）；TP → DP 回带不确定性的未来轨迹、进入各机巢服务范围的时刻、前提有效性 |
| 求会面点 | DP → RS 求本组合会面点（机型速度、机巢起点、风况修正、船舶预测轨迹）；RS 解相对运动拦截关系；RS → DP 回「追不上」（无需返程电量判断，直接淘汰）或「会面点 ＋ 会面时间窗 ＋ 理论飞行时长」 |
| 出航迹与回填 | DP → RP 请求航迹（起点机巢 → 终点会面点）；RP 避让禁飞区、桥梁净空、预留沿江可迫降点；RP → DP 回可飞航迹 ＋ 精算飞行时长 ＋ 精确能耗 |
| 出航迹与回填 | DP 反推并回填起飞时刻；DP → RP 补做航迹级空域冲突二查；RP → DP 回冲突结论；DP 按「先错峰 → 再绕行 → 都不行才回退换候选（仅派单阶段、起飞前）」处置 |
| 出航迹与回填 | DP 偏差回验：精算时长与粗估偏差过大则退回重验电量**与「回原巢是否仍成立」**（见 `21` §2 第 5 步） |
| 去程纠偏 | DP → FC 下发任务方案（机、巢、会面点、起飞时刻） |
| 去程纠偏 | 新遥测（共享数据源／M4 写入）触发 M3（`33`）纠偏循环；M3 → TP（M2 常驻层）重估「船未来会到哪」；TP → M3 回更新后的预测与前提有效性 |
| 去程纠偏 | M3（`33` 纠偏循环）→ RS（`32`）以同一机、同一巢重算会面点；RS → M3 回更新后的会面点 |
| 去程纠偏 · 6a | M3 纠偏循环：小幅抖动不改指令；偏差超阈值且前提仍成立时只重算这一架机的会面点并下发新指令（减速、加速、避让、换道） |
| 去程纠偏 · 6b | M3 纠偏循环判定前提已失效 → 上报 M2（DP）：变的是「船怎么走」，原预测已不适用；M2 → TP 重算轨迹；M2 重跑剪枝与择优：改会面点或放弃本次会面 |
| 末段 | FC 保持相对速度趋近于零、相对位置稳定于甲板上方；四子阶段：接近 → 匹配 → 交接 → 脱离 |
| 末段 | 对接失败：重试、悬停等待、放弃本次会面转兜底 |
| 末段 | RS → DP 交接完成确认（含伴飞与交接的时间、能耗开销）；飞控只执行与回传实况，判定归 M3 |
| 收尾 · 数据回流 | 实际能耗、实际会面偏差、轨迹预测误差由 M4、M3 回流至 M2（发起方见 §5 数据回流行）；DP → RS 校准纠偏阈值与会面策略偏好；DP → TP 校准预测模型参数 |

> **注**：上列「去程纠偏」各行原把驱动方写作 FC，与 §5 硬约定 2「闭环只经 M2 闭合，不允许旁路」、`20` §3 约定 2「M3 只在被调用时求解」、`33-M3-路径规划` §3.5「去程段是常规流程里唯一的循环体」（循环在 `33`）三处口径不一致。**已由组长裁定（2026-10-10，见 §7.2 U-01）：驱动方为 M3（`33`）纠偏循环、FC 不直连 TP／RS**；上述各行已据此订正。
