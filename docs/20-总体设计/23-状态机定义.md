## 1 权威性

1. 本文是**状态机的唯一权威处**。其余文档只写「见 23」，不再各自枚举状态。
2. 历史上的四套并行版本——`31` 的船舶与订单状态、`34` 的订单时间线、`37` 的订单与货物状态、`35` 的订单时间线——**均属已废弃写法**（禁用对照见 §9），一律以本文为准，批 3 重建模块文档时已逐处替换。
3. 单一来源原则：**同一个业务对象只有一套状态集**。订单与任务的阶段关系由 §5 的派生规则约束，不允许「订单一套、任务另一套」并存。

## 3 订单状态机

| 状态 | 归属 | 说明 |
|---|---|---|
| 待受理 | 订单 | 订单已创建，接单判定尚未完成 |
| 已受理待唤醒 | 订单 | 受理但不派单。**唤醒原因三类**：等船（尚未驶入系统服务航段）、等货（货物未备好）、**闸门熔断／数据不足**（派单闸门处于熔断中，或关键数据不足暂缓派机；由 A 组 `AdmissionResult` 给出，见下表） |
| 待调度 | 订单 | 已满足派单前置门，进入派单队列，等待本批求解 |
| 调度中 | 订单 | 第 2–5 步求解中 |
| 已派发 | 订单（任务投影） | 起飞时刻已回填，任务已下达 |
| 去程中 | 订单（任务投影） | 对应第 6 步 |
| 末段交接中 | 订单（任务投影） | 对应第 7 步 |
| 返航中 | 订单（任务投影） | 对应第 8 步 |
| 已完成 | 订单（任务投影） | 交接成功 |
| 已拒绝 | 订单 | 业务边界不满足，或第 3／5 步无可行组合 |
| 失败 | 订单 | 迫降野外，转人工回收 |
| 异常终止 | 订单 | 货物灭失 |

流转约束：

1. 正向唯一路径：`待受理 → 已受理待唤醒 → 待调度 → 调度中 → 已派发 →（去程中 → 末段交接中 → 返航中）→ 已完成`。
2. `已受理待唤醒` 可跳过：机场在服务航段内且货物已就绪时，受理后直接进入 `待调度`。
3. 三个终止态 `已拒绝`、`失败`、`异常终止` 互斥，进入后不再流转。
4. 第 4 步「综合择优与资源级占位定案」完成后订单进入 `已派发`；若第 5 步精算回填后复核不通过且降级到次优组合仍不可行，回到 `已拒绝` 并说明理由。
5. 归巢余量不足、他巢临时停靠的情形不改变订单状态，只改变任务的落点（见 §5）。
6. `已受理待唤醒 → 待调度` 的唤醒条件由 `wakeReason` 承载，**四对一映射见下表**（A 组 `AdmissionResult.decision` →本文 §3 状态，C-08；写入方 M2，见 §8）。

**`AdmissionResult` → 订单状态映射（C-08，四对一）**

| `decision` | 订单落点 | 说明 |
|---|---|---|
| `ACCEPT` ＋ 可立即派单 | `待调度` | 直接进队列 |
| `ACCEPT` ＋ 需等待 | `已受理待唤醒` | 带 `wakeReason`＝等船／等货／闸门熔断／数据不足 |
| `DEFER` | `已受理待唤醒` | 延后触发调度，同上带 `wakeReason` |
| `REJECT` | `已拒绝` | 带拒绝原因码 |
| `MANUAL` | `已拒绝`（转人工） | `MANUAL` 落点；人工接管后由 M2 改写状态并留痕 |

> **`wakeReason` 两类补充（C-08 关联）**：A 组《接口回执提交说明》指出原文只列了等船／等货两类，本版按 A 组要求补入**闸门熔断**与**数据不足**两类。**映射表的算法层源为 `80` §2.3 `AdmissionResult`。2026-10-11 D 组回执确认**：该表与 `83` §2.5 派单闸门口径一致，四类 `wakeReason` 确认；`MANUAL → 已拒绝`（转人工，M2 以 `trigger_source` 留痕）亦经 D 组同意（放弃原「待人工处理」独立状态主张，避免触碰三终止态互斥约束）。**本节已转最终口径。**
>
> **「等运力」不占 `wakeReason`（D 组 2026-10-11 说明）**：功能 8 的「等运力」（占位冲突失败回队）属**队列层重试行为**，由资源释放事件触发重入批次，不进入「已受理待唤醒」态；若后续要把等运力订单也置入 DEFER 态，需另行议定，本轮不改。

## 4 任务状态机

| 状态 | 进入条件 |
|---|---|
| 已派发 | 调度引擎完成第 5 步精算与起飞时刻回填，任务方案下发 M4 |
| 去程中 | M4 确认起飞（第 6 步） |
| 末段交接中 | M3 判定进入会面点邻域（第 7 步） |
| 返航中 | 交接完成确认，进入第 8 步 |
| 已完成 | 落巢确认（原驻巢或他巢迫停均算任务闭环，落点另记） |

异常分支：

| 状态 | 进入条件 | 后续 |
|---|---|---|
| 迫停中 | 返航复核判定回不了原驻巢，向近处机巢申请应急迫停并获准入 | 落他巢后转 `已完成`，落点记为迫停巢 |
| 迫降待回收 | 无可借机位，转入应急迫降点 | 转人工回收；对应订单进入 `失败` |
| 异常终止 | 无人机灭失判定成立 | 货物 `灭失`，订单 `异常终止` |

约束：

1. 任务状态只由 `已派发` 起算，不含 `待受理` 一类订单阶段。
2. 飞行中途的 `6b 意图变更`、风速突变、临时禁飞不新增任务状态，只触发调度侧重跑；状态仍停在 `去程中`。
3. 末段内部的四子阶段（接近、匹配、交接、脱离）不建为独立任务状态，属于 `末段交接中` 的内部过程。

## 5 订单与任务的派生关系

订单与任务不是两套并行的状态机，而是「一单一个订单状态 ＋ 一次飞行一个任务状态」，二者在任务存在期间**取值保持一致**：

1. 任务建立时（第 4 步定案、第 5 步回填），订单写入 `已派发`，同时 `mission.status` 初值同为 `已派发`。
2. 任务推进时，`mission.status` 的任何变更在**同一事务内**回写 `order_task.status`。
3. `35-M5-终端交互` 的船员端「订单状态时间线」（`待调度 → 已派发 → 去程中 → 末段交接中 → 返航中 → 已完成`）展示的即投影后的订单状态，不再单独维护一条时间线。
4. 订单侧独有的状态（`待受理`、`已受理待唤醒`、`待调度`、`调度中`、`已拒绝`）不写任务表；任务侧独有的异常态（`迫停中`、`迫降待回收`）不在订单侧展开，由落点字段与订单终止态表达。

> 本派生规则是本文的裁决，用于消除「订单一套、任务另一套」的历史分歧。批 3 重建 `37` 时，`order_task.status` 与 `mission.status` 的字段说明按本节改写，并在 `27-一致性约束` 里明确同一事务边界。

## 6 货物状态机

| 状态 | 说明 |
|---|---|
| 未就绪 | 拣选、打包中 |
| 已就绪 | 备好并通过检查，满足派单前置门 |
| 已装机 | 随无人机离巢。此后货物绑死在该机上，空中不可转移 |
| 已交付 | 与船交接完成 |
| 已回收 | 随原机落巢后被系统回收，状态转为可用，构成重派唯一入口 |
| 灭失 | 随无人机灭失，订单异常终止 |

约束：

1. `已装机 → 已交付` 与 `已装机 → 已回收` 互斥：交接成功走前者，未送达随原机落巢回收走后者。
2. 迫降在应急迫降点**不构成回收**，货物落在系统设施之外，须人工回收后再入队。
3. 当前载体与当前位置必须持续跟踪，位置不是「记一笔」而是重派剪枝的必要输入。

## 7 无人机状态机

| 状态 | 说明 |
|---|---|
| 空闲 | 可进入候选。唯一可被 L5 占位的状态 |
| 已预占 | L5 占位成功至起飞前的窗口 |
| 执行任务中 | 从起飞到交接完成（含去程、末段） |
| 返航中 | 交接完成至落巢 |
| 迫停 | 临时停靠他巢，归属不变 |
| 迫降 | 落在应急迫降点 |
| 故障 | 设备异常，须检修 |
| 维护 | 计划检修、保养 |
| 失联 | 心跳超过判定窗口未收到；失联不等于灭失，持续超过灭失判定窗口才推定灭失 |

流转：

```
空闲 ──L5 占位──▶ 已预占 ──起飞──▶ 执行任务中 ──交接完成──▶ 返航中 ──▶ 空闲
                     │                  │                        ├──▶ 迫停 ──回收──▶ 空闲
                     │                  └──心跳超窗──▶ 失联      └──▶ 迫降 ──人工回收──▶ 维护 ──▶ 空闲
                     └──占位释放──▶ 空闲       失联 ──▶ 返航中 ／ 迫降
任一状态 ──检修、故障──▶ 维护、故障
```

约定：

1. 无人机侧状态名用 `执行任务中`（旧名见 §9 禁用写法表），以区别于订单、任务上下文里同形的旧写法，避免同一词指两个对象。
2. 展开候选时只取 `空闲`：在飞、在充电、充电中待派一律不进候选（充电中可中断派出属可选项，当前未启用）。
3. 迫停不改变 `homeNestId`，只改 `currentNestId`。

## 8 状态写入方

| 状态变更 | 写入方 | 触发 |
|---|---|---|
| 订单 `待受理 → 已受理待唤醒`／`待调度` | M2 | 第 1 步受理判定 |
| 订单 `待调度 → 调度中` | M2 | 第 2 步起开始求解 |
| 订单 `调度中 → 已派发` | M2 | 第 4 步定案并通过第 5 步回填 |
| 订单／任务 `已派发 → 去程中` | M4 | 起飞确认 |
| 任务 `去程中 → 末段交接中` | M4 | 收到 M3 的进入邻域判定 |
| 任务 `末段交接中 → 返航中` | M4 | 交接完成确认 |
| 任务 `返航中 → 已完成` | M4 | 落巢确认 |
| 任务 `→ 迫停中`／`迫降待回收` | M4 上报，M2 决策 | 返航复核与应急迫停准入 |
| 订单 `→ 已拒绝` | M2 | 第 3／5 步无可行组合 |
| 订单 `→ 失败` | M2 | 迫降野外，转人工回收 |
| 订单 `→ 异常终止` | M4 判定灭失后上报，M2 终止 | 灭失判定成立 |
| 货物 `未就绪 → 已就绪` | M5 人工确认／仓储录入 | 拣选打包完成并通过检查 |
| 货物 `已就绪 → 已装机` | M2 | 装机确认（离巢前） |
| 货物 `已装机 → 已交付` | M4 | 与船交接完成 |
| 货物 `已交付 → 已回收` | M2 | 落巢回收完成；野外迫降须人工回收后由 M5 确认 |
| 货物 `→ 灭失` | M4 判定并上报 | 灭失判定成立 |
| 无人机 `空闲 → 已预占` | M2 | L5 占位成功 |
| 无人机 `已预占 → 执行任务中` | M4 | 起飞确认 |
| 无人机 `执行任务中 → 返航中` | M4 | 交接完成 |
| 无人机 `返航中 → 空闲`／`迫停`／`迫降` | M4 上报，M2 复核 | 落原巢／他巢获准入／野外迫降 |
| 无人机 `→ 失联` | M4 | 心跳超过判定窗口 |
| 无人机 `→ 故障`、`→ 维护` | 人工（M5 干预台） | 故障上报、计划检修 |

原则：**检测归 M4，决策归 M2，落库归 M6**。M4 只做事实检测与上报，不自行改判可行性；M6 只负责存储与一致性，不判断流转。

## 9 状态词禁用表

| 禁用写法 | 唯一写法 | 说明 |
|---|---|---|
| 待派发、待派单 | 待调度 ／ 已派发 | 视上下文而定；`待派单` 一律废弃 |
| 已分配 | 调度中 | 订单侧 |
| 执行中（订单、任务上下文） | 去程中 ／ 执行任务中 | 无人机侧允许写作 `执行任务中` |
| 派单中 | 调度中 | 订单侧 |
| 完成、投送完成 | 已完成 | — |
| 拒单（正式文本） | 已拒绝 | 口语可用 |
| `status` 里出现中文以外的同义枚举 | 见 §3–§7 | 落库枚举一律用本文写法 |
