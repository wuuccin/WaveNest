## 1 架构总览

系统采用「一条数据主干 ＋ 一个调度主控 ＋ 一个求解服务 ＋ 一条监控旁路 ＋ 一层展示 ＋ 一层存储」的形态。

```
              外部世界
   AIS   无人机遥测   气象   水文   航道与空域公告
    │        │         │      │          │
    └────────┴────┬────┴──────┴──────────┘
                  ▼
        ┌───────────────────┐
        │  M1 数据采集       │  连接器 → 解码器 → 发布器
        └─────────┬─────────┘
                  │ 结构化态势（只接入一次）
                  ▼
        ┌───────────────────┐        ┌───────────────────┐
        │  M2 调度引擎       │◀──────▶│  M3 动态会面      │
        │  （唯一调度主控）   │  循环   │  路径规划         │
        │                    │  调用   │  （求解服务）      │
        └────┬────────┬─────┘        └───────────────────┘
             │        │
             │        └──────────▶ ┌───────────────────┐
             │                     │  M4 飞行任务监控   │◀── 无人机链路（MQTT）
             │                     │  （监控旁路        │
             │                     │    链路网关）      │
             ▼                     └─────────┬─────────┘
        ┌───────────────────┐                │
        │  M6 数据库与缓存   │◀───────────────┘
        │  （一切状态的落点） │
        └─────────┬─────────┘
                  ▼
        ┌───────────────────┐
        │  M5 终端交互       │  只读展示 ＋ 人工干预入口
        │  可视化            │
        └───────────────────┘
```

主干：`M1 采集 → M2 估计与预测 → M2 展开与剪枝（循环调 M3 求会面点）→ M2 择优占位（M6 记账）→ M2 请 M3 出航迹并回填起飞时刻 → M4 监控 ＋ M3 纠偏 → M3 末段交接 → M2 返航复核 → M3 出返航航迹 → 货物回收重入队 → M4 数据回流校准`。

角色分工：

| 模块 | 在架构中的角色 |
|---|---|
| M1 数据采集 | 数据源头，全系统唯一接入层 |
| M2 调度引擎 | **唯一调度主控（hub）**，接单、剪枝、择优、占位、回填、重调度、返航复核 |
| M3 动态会面、路径规划 | 被 M2 循环调用的**求解服务**；去程与返程航迹同属一项能力 |
| M4 飞行任务监控 | 监控与告警的**旁路**，兼无人机链路网关 |
| M5 终端交互、可视化 | 全程只读展示 ＋ 人工干预入口 |
| M6 数据库、缓存 | 所有状态的落点，不做业务判断 |

## 2 常驻层

常驻层不是流程步骤，而是**全程在线的地基**：不因订单启停，从系统开机起持续运行。

```
M1 五路连接器持续接入 → 解码器解析 → 发布器投递
        ↓
M2 状态估计（去噪、去重、丢包外推，回答「此刻在哪、多快、朝哪走」）
M2 常驻预测（在其之上推「未来会到哪」，全量、滚动刷新）
        ↓
M6 承接落点：实时最新状态写 Redis，历史轨迹落 ship_ais 等表
        ↓
M5 从开机起就在工作：大屏与后台读「当前态势」
```

环流：`M1 采集 → M2 估计与预测 → M6 存储 → M5 展示`。

三条硬约束：

1. **常驻预测覆盖范围必须外扩于系统服务航段**。船尚在段外时也要有预测数据，否则第 1 步「会不会驶入」无从判断。
2. **常驻预测与第 2 步的精算预测是一套实现、两种触发**：常驻滚动更新，接单时按需取用快照。禁止做成两套代码。
3. 常驻层的价值在广度（全量、持续、随时可取），第 2 步的价值在深度（单船、精细、带不确定性）。飞行中纠偏全程依赖常驻层，不能当作预处理。

## 3 模块依赖关系

| 模块 | 运行期依赖 | 被谁依赖 |
|---|---|---|
| M1 数据采集 | 外部数据源、无人机与机巢链路 | M2、M3、M4、M5、M6 |
| M2 调度引擎 | M1（原始态势）、M3（会面点与航迹）、M6（台账读写） | M3、M4、M5、M6 |
| M3 动态会面、路径规划 | M2（状态与预测、任务参数）、M1（气象、水文、空域约束）、M6（迫降点台账与底图约束） | M2 |
| M4 飞行任务监控 | M1（遥测）、M2（任务方案）、M6（落库） | M2（偏差与告警）、M5（推送）、M6（写入） |
| M5 终端交互、可视化 | M2、M3、M4（数据）、M6（查询） | —（终端用户） |
| M6 数据库、缓存 | 无（基础设施层） | 全部模块 |

依赖方向的约定：

1. **M2 是唯一的调度主控**。M3 不主动发起调度，只在被调用时求解；M4 不自行判断可行性，只检测与上报；M5 不直接调用算法模块。
2. **闭环只经 M2 闭合**。飞行中要改方案，路径是 M3／M4 → M2 → 重跑，而不是 M3 自行决定。
3. **M6 不做业务判断**。状态由业务模块写入，M6 只保证「写得对、读得一致、可追溯」。

## 4 链路归属

无人机遥测与飞行指令同属一条 MQTT 链路，收发同源，但职责分属两个模块：

| 方向 | 承担方 | 说明 |
|---|---|---|
| 下行：遥测接入与解码 | **M1** | 全系统**只接入一次**；M4 不直接订阅 MQTT 主题，改从 M1 交付的遥测流取用 |
| 上行：飞行指令判定与编码 | **M4** | 指令由 M4 判定与编码，**经 M1 已建立的 MQTT 通道下发**；M1 只做通道与编码适配，不判断「该不该发」 |

清洗分三层，各做一次，不重复：

| 层级 | 内容 | 承担方 |
|---|---|---|
| 格式级 | 字段范围、时间戳合理性、基本去重 | M1 |
| 船舶状态估计 | 去噪、去重、丢包外推 | M2 |
| 飞行语义级 | 野值剔除、短时丢包外推 | M4 |

订单数据不属 M1：接单判断与订单接入归 M2。

## 5 职责边界

| 模块 | 做什么 | 不做什么 |
|---|---|---|
| M1 数据采集 | 五路接入、解析、格式级校验、投递结构化消息、链路健康可观测 | 不做状态估计、不做坐标与单位归一、不判断业务、不建业务表 |
| M2 调度引擎 | 接单判定、状态估计与预测、候选展开与剪枝、择优与占位、起飞时刻回填、飞行中重调度、返航复核、结果记录 | 不求解会面点、不生成航迹、不检测飞行异常、不直接落库 |
| M3 动态会面、路径规划 | 会面点求解、可飞航迹生成（去程与返程同一能力）、去程段纠偏与前提失效判定、末段伴飞与交接判定 | 不选机、不占位、不自行决策兜底（返航或迫停由 M2 决定） |
| M4 飞行任务监控 | 遥测取用与飞行语义级校验、任务进度与状态流转记录、轨迹偏差计算、异常检测与告警、飞行数据记录与回放、上行指令判定与编码 | 不判断「还能不能飞完」、不做是否返航的决策、不重新接入与格式级校验遥测 |
| M5 终端交互、可视化 | 展示算法层产出、船员下单入口、人工干预指令回传、时间轴回放 | 不做业务决策、不直接碰算法、不提供「把货物直接改派给另一架机」 |
| M6 数据库、缓存 | 落库、缓存、坐标与单位归一、统一访问接口、并发与一致性保障 | 不判断货物流转、不承载业务决策 |

三条容易被越界的线：

1. **检测与决策分家**：异常检测永远归 M4，可行性判断永远归 M2。两边各算一套余量会给出相反结论。
2. **货物转移的物理边界**：货物离巢后绑死在该机上，空中无法转移；凡涉及「换一架机接着送」，一律表述为「货物回收后重派」（见 21 §8）。
3. **图与正文冲突时以正文为准**：图内与正文不一致的表述一律按正文修正。时序图已重画为图集目录 `91-时序图/`（导览页 ＋ 九张图），其余图集内的旧口径随后修正。
