──────── Project Summary ────────

### Top Issues

1. **Record types declare invariants in Javadoc but never enforce them — the dominant failure mode.** Nearly every cross-layer value object in `backend/wl-algo/.../meeting/model/` and `backend/
wl-m3-rendezvous/` lacks a validating compact constructor, so malformed data propagates silently instead of failing loudly. Representative cases:
   - `algo/meeting/model/`: `B_FlyableRoute`, `B_HandoverConfirmation`, `B_TakeoffTimeResult`, `ConflictSpaceTime`, `CpaPoint`, `ShipPoint`, `ShipState`, `Wind`, `RendezvousSolveRequest`.
   - `m3-rendezvous/`: `RendezvousCommand`, `RendezvousRecalcRequest`, `RecalcOptions`, `SegmentedWaypoint`, `SegmentedTrack`, `TakeoffTimeCommand`, `GenerateRouteCommand`, `HandoverCommand`, `
DroneContext`, `MissionTrackCommand`.
   Sibling records in the same packages *do* validate (`B_RendezvousSolution`, `WindSnapshot`, `HandoverSample`, `RecalcStateSnapshot`), so this is an inconsistency, not a deliberate convention
. Root cause: the validation pattern was applied ad hoc rather than as a package-wide rule.

2. **The "version consistency" hard constraint is broken end-to-end.** `ShipTrackSnapshot.version` is unvalidated, `RendezvousCommand.snapshotVersion` is unvalidated (while `RendezvousRecalcReq
uest` validates the same field), and `RendezvousSolveService` folds a *missing* version into `SnapshotVersionMismatchException` rather than a request error. Consequence: `RendezvousSolver` buil
ds `solutionId = "RS-<combo>-null-<now>"` and propagates `null` into `B_RendezvousSolution.snapshotVersion`. This directly violates the documented「 版 本 一 致 性 是 硬 约 束 」 and is the highest-impact
 data-integrity issue.

3. **Dead/unreachable guards that mask real invariants.** Multiple checks are provably unreachable, hiding the fact that the real precondition is unchecked elsewhere:
   - `RendezvousRecalcService` re-checks `droneId` non-null/non-blank and `request.snapshotVersion() == null`, both already enforced by the record's compact constructor.
   - `TrackInterpolator` and `TrackConflictChecker.interpolate` both end with an unreachable `return last;` after an early `t >= last.t()` return.
   This is a symptom of the same missing-validation problem (#1): guards get scattered into services instead of living at the type boundary.

4. **Enum wire-contract handling is inconsistent across the codebase.** `HandoverResult` exposes `getValue()` as the「 对 外 口 径 」 but has no `@JsonValue`/`@JsonCreator`, so Jackson serializes the
 enum name and round-trips fail. `TakeoffInfeasibleReason.fromValue` and `TrackSegment.fromValue` lack the null/blank/`trim()` guards that the sibling `NoSolutionReason.fromValue` has. `TrackSe
gment` also doesn't enforce uniqueness of `value` strings, so a duplicate silently returns the first match.

5. **Mutable collections leak out of immutable records.** `ShipTrackSnapshot` stores `points` by reference, `SegmentedTrack` accepts an empty/non-monotonic list, and `TrajectorySnapshotPort` ex
plicitly promises a "read-only, shareable" snapshot that its return type cannot deliver. Downstream algorithms assume time-ascending, stable ordering — this assumption is neither enforced nor p
rotected.

6. **Numeric overflow and degenerate-input handling in the trajectory module.** In `TrackGenerator`: `(int) Math.round(distanceM / speedMs)` saturates silently for tiny speeds; segment-boundary
 waypoints are duplicated (same coordinate *and* timestamp); and `routeVersion` derived only from `routeId + startMs` produces identical versions across geometry-changing recalculations. `Missi
onTrackCommand.takeoffMs` can overflow when large values feed `takeoffMs + Math.round(k * tauFine * 1000.0)`.

7. **Antimeridian / geographic range inconsistencies.** `TrackGenerator` computes τ from `GeoApprox.distanceM` (which normalizes Δlon into (−180, 180]) but interpolates raw `endLon - startLon`,
 so legs crossing ±180° produce wrong waypoints. `MissionTrackCommand` relies on exact `==` double equality for degenerate-leg detection, missing the `lon = 180` vs `lon = -180` case. `Generate
RouteCommand` validates finiteness but not geographic bounds, so projected/pixel coordinates pass through as lon/lat.

8. **Inconsistent invalid-input contracts.** `RendezvousRecalcRequest` throws `NullPointerException` for nulls but `IllegalArgumentException` for blanks; `SegmentedTrack` throws bare NPE from `
List.copyOf` for a null element but an informative IAE for a null list; `DeviationTracker` defers length/premise checks to the algorithm layer (`CrossTrackError`, `PremiseVerdict`) with a diffe
rent exception type. Callers must handle multiple failure modes for the same class of bad input.

9. **Unenforced algorithmic assumptions.** `RendezvousSolver`'s bisection assumes `g(t) = d(t) − v·(t−tLo)/1000` is monotone decreasing, but `d(t)` is not monotone for a turning/receding ship,
breaking the「 取 最 早 满 足 者 」 contract. `TrackConflictChecker` is O(samples × waypoints) because `interpolate` restarts at index 0 each call, and `ConflictParams.sampleStepMs` has no upper bound
(a huge `sys_param` silently reduces the scan to a couple of samples).

10. **Dead build configuration.** `wl-m3-rendezvous/build.gradle.kts` declares `libs.bundles.web.common`, `wl-contract`, and `wl-storage` with no corresponding imports in the module sources — t
he module is a plain `java-library` business module.

### Cross-Cutting Concerns

- **Validation is opt-in per type, not a package contract.** Compare `RendezvousCommand` (unvalidated `snapshotVersion`/`nowMs`) with `RendezvousRecalcRequest` (validates the same field), or `W
ind` (no validation) with `WindSnapshot` (validates speed and finiteness). See `algo/meeting/model/Wind.java`, `m3-rendezvous/solver/RendezvousCommand.java`, `m3-rendezvous/solver/RendezvousRec
alcRequest.java`.
- **Blank-vs-null asymmetry for identifiers.** `DroneContext.comboId`, `MissionTrackCommand.comboId`, `RendezvousCommand.snapshotVersion`, and `ShipTrackSnapshot.version` accept blank strings w
here siblings reject them. Adopt a single `requireNonBlank` helper across value objects.
- **Boxed-vs-primitive and nullable-field inconsistency within a single record.** `B_HandoverConfirmation` mixes primitive `plannedMeetLon/Lat/plannedMeetT` with boxed `actualMeetLon/Lat/handov
erDoneT`; `B_RendezvousSolution` box-checks only some fields on the no-solution branch. Same pattern recurs in `HandoverParams` (enforced bounds undocumented) and `RecalcStateSnapshot` (all-or-
nothing drone-field coupling stricter than the documented contract).
- **Non-finite/out-of-range doubles accepted at the algorithm boundary.** `GeoApprox.distanceM`/`bearingDeg`, `EffectiveSpeed`, `CpaPoint`, and `ShipState` all take raw doubles that flow from `
RendezvousSolver.solve()` without finiteness checks, producing silent `NaN` propagation.
- **Missing @JsonValue/@JsonCreator on all "对 外 口 径 " enums.** `HandoverResult` is the clearest case; `TakeoffInfeasibleReason` and `TrackSegment` share the parsing weakness.
- **Exceptions that don't retain structured data.** `SnapshotVersionMismatchException` interpolates expected/actual into the message only; callers can't read them for metrics or reconciliation.
- **Port contract vs. actual types.** `TrajectorySnapshotPort` promises shareable/read-only but returns a record wrapping a mutable `List`; `DroneContextPort` Javadoc contradicts itself on the
`droneId` precondition; `RendezvousFacade` stores injected ports with no null check, deferring assembly failures to deep NPEs.
